# run取消・手動再試行・attempt履歴API

管理API `ci_runner.app:app` をloopbackにbindして使う。全HTTP経路で単一のloopback `Host` を要求し、bodyやDBを処理する前に違反を403で拒否する。`X-Forwarded-Host` は許可判定に使わない。公開Webhookアプリの受信口とは別。DB接続やtransactionに失敗した場合は共通の503応答を返す。

## 管理画面

ライブは `/ui`。実行一覧からの選択または実行ID検索で詳細へ進み、コミットSHA、試行の状態・種別・理由・終了コード、正式結果を確認できる。
一覧と試行履歴は20件ずつ。時刻はUTC。詳細の実行情報、表示中の試行、再試行の可否は、読み取り専用の同じPostgreSQL snapshotから得る。

操作ボタンは下記と同じPUTを同一オリジンで送信する。再試行は受付時にもDBで再判定する。
対象が変わった、または応答を確認できなかったときは、画面から現在の状態を確認する。
正式ログのリンクは表示時点の試行IDを固定する。再試行後に同じリンクを開くと409になり、詳細への戻り口を表示する。

`/ui/demo` のIDと時刻は過去の試験シナリオを再現するための固定例。操作を提供せず、DB停止中も閲覧できる。
HTMLとCSS、操作スクリプトは管理APIから配信する。外部リソースへの接続や埋め込みをCSPで制限し、Hostは管理操作と同じloopbackに限定する。

## 正式な結果成果物

「結果JSONを保存」は `GET /runs/{run_id}/artifacts/result?attempt_id=<UUID>` を開く。正式参照と指定IDが一致し、保存済みのバイト列がある場合に200。
応答は添付の `result.json` と `X-Artifact-SHA256` を返す。参照が解除または変更された場合は409、実行または成果物がなければ404。

Workerの確定処理がrun ID、試行ID・番号、受理SHA、結果・終了コード・理由、実行時間、検証済みsourceの由来からJSONを生成する。
保存キーは `<attempt-id>/result.json`。DB内のキーとして扱う。固定fixtureの出力ログは従来のログ経路で参照する。
1試行1件・最大4KiB、保持payload合計16MiB。上限超過時はログ・成果物・結果の確定をすべてロールバックする。
成果物生成後の停止でもDBトランザクションの成否で可視性が決まり、別領域の一時ファイルの回収は発生しない。
再試行後も旧成果物の履歴はDBに残る。ダウンロードは現在の正式結果だけに限定する。
版7以前の履歴は成果物なしとして扱う。保持期限と自動削除は未実装。上限の対象はpayloadのバイト数。

## 運用指標

`/ui/metrics` と `GET /metrics/operations` は、許可workflowで直近24時間に終了した最新1,000試行までを集計する。

| 指標 | 定義 |
|---|---|
| キュー待ち時間 | claim時に記録した取得可能時刻からDB上の開始時刻まで。自動再試行のバックオフは除く |
| Worker実行時間 | Workerの単調時計によるDockerの起動から終了確認まで。事前のソース取得・build、終了後の回収・DB確定は別工程 |
| 基盤障害率 | `infra_lease_expired` と `infra_exhausted` の件数を対象の完了試行数で割る |
| 実行権の期限切れ | 上記2種類に `canceled_lease_expired` を加えた件数 |

待ち時間と実行時間は平均、p95、計測件数を表示する。旧版で計測値がない試行や、実行時間を記録できなかった失効は、該当指標の母数から除く。
基盤障害の分類にはDBへ記録された理由を使う。実行権が発行される前の取得障害や、終了前の処理はこの集計に含まれない。

## runの取消

`PUT /runs/{run_id}/cancel` はリクエストbodyなし。ブラウザーからの同一オリジン操作とCLIに使う。許可Hostは `localhost`、`127.0.0.1`、`[::1]`。管理APIにはCORSを設定せず、loopbackだけで待ち受ける。

| 対象run | 結果 |
|---|---|
| 待機中 | 200。DB時刻を記録して `canceled`。新規attemptは作らない |
| 実行中 | 202。DB時刻に取消要求を記録し、実行権を閉じるまで `running` |
| 取消済み、または同じ取消要求の再送 | その時点の状態を返し、元の要求時刻を保持 |
| 成功・失敗・時間切れ | 409。正式結果と履歴を維持 |
| 対象なし、許可対象外、UUID不正 | 404または422 |

取消要求と結果確定は同じrun行ロックで順序が決まる。取消要求のcommit後はpreflight・heartbeat・成功報告が拒否され、期限監視が `canceled_lease_expired` を記録する。残存コンテナは通常の回収手順に従う。現在の常駐Workerはheartbeat拒否を受けると所有資源を回収し、安全停止する。後続処理には監視側からの再起動が必要。

取消の応答はDB commit後に返す。応答喪失時は同じPUTを再送できる。HTTP 202は取消要求の保存を示す。実行停止の確認には状態とattempt履歴を参照する。

## 手動再試行

`PUT /runs/{run_id}/retry/{attempt_id}` はbodyなし。同じloopback Host条件を適用する。`GET /runs/{run_id}/attempts` で確認した最新の失敗attemptを指定する。

| 条件 | 応答 |
|---|---|
| `failed` / `timed_out` の正式結果、または作成未送信・不在確認済みの基盤障害 | 202。`run_id`、`previous_attempt_id`、`requested_at` を返す |
| 受付済みのrunとattemptの組を再送 | 同じ202と元の受付記録。現在のrun状態は `GET /runs/{run_id}` で確認する |
| 遅延した未受付の要求、待機中、実行中、成功、取消、回収未確認の基盤障害 | 409。`--claim-once` から再試行を取得することもできない |
| runなし、許可対象外、UUID不正 | 404または422 |

run行を先にロックして最新attemptを照合する。新しい受付記録、`queued` への遷移、正式結果参照の解除を同じtransactionでcommitする。
期限監視が先に同じrunを再キューした場合は409。手動受付が先に確定した場合は、その要求を起点として直ちに待機キューに入る。
旧attemptとログ・取得元は保持する。正式ログAPIは、新しい正式結果が確定するまで409を返す。

検証付きWorkerが同じrun IDと受理SHAを再検証し、新しい通算番号・token・30秒leaseを発行する。
明示的な再取得は `manual`、同じ区間で失効後に再取得する場合は `infrastructure`。新しい区間ごとに最大3attempt、5秒・10秒のバックオフを適用する。

## attempt履歴

`GET /runs/{run_id}/attempts` はattempt番号の降順で返す。 `limit` は既定20、範囲1〜100。次がある場合は `next_before` を排他的な `before` に渡す。存在するrunに履歴がなければ空の200、runがなければ404。

一覧はattempt番号、再試行種別、状態、開始・終了時刻、終了コード、理由、`official` を返す。 `official` は同じSQL snapshotで確認した正式attempt参照に一致する場合に真。実行権tokenやログ本体は含めない。正式ログは既存の [run IDによるログ参照](log-access.md) で取得する。
