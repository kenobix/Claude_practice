# MVP進捗の概算と完了判定

基準は[261014計画](../../../261014/plan_ci_runner.md)のP0〜P5。テスト件数やcommit数ではなく、
受入条件に対する実装・検証済み範囲を見て推定する。経過工数や残時間の実測ではない。

| Phase | 計画工数の中央値 | 達成度の推定 | 根拠と主な残件 |
|---|---:|---:|---|
| P0 | 13h | 100% | 現環境・管理下fixtureの設計/実行制限を実測。非信頼コード隔離は対象外 |
| P1 | 23h | 100% | 受付/永続化/冪等性、受理commitの単一常駐Workerと停止、結果/ログ/由来。管理下fixtureで受入確認済み |
| P2 | 30h | 100% | 2 Workerのclaim競合、DB時刻によるlease・再試行、heartbeat断、Docker回収、停止位置別の復旧と旧報告拒否を検証済み |
| P3 | 16h | 75% | 元bodyの署名検証、配送重複排除、runと配送の同時保存をローカルHTTPS・実DBで検証済み。GitHubからの実配送と手動再送が残る |
| P4 | 20h | 0% | 操作/履歴UI、取消/手動retry、一般成果物、観測は未実装。P1のログ参照を二重加算しない |
| P5 | 21h | 10% | 再現/故障記録の一部あり。比較計測・3分demo・第三者再現/最終レビューは未実施 |

中央値合計123hに対して、重み付きの推定達成分は80.1h相当で、**概算約65%・残約35%**。
達成度は設計判断を含む主観的な見積りで、時間消化率や完成保証ではない。独立レビュー・新たな障害で再評価する。
P0〜P2は管理下の固定fixtureで受入確認済み。P3はGitHubからの実配送の受入待ち。

PR #4で公開した固定fixtureは、受理commitから取得し、同じrunで一件実行して由来を保存できる。
単一Workerの常駐・停止と受理commitの4モードを実測した。[P1受入判定](p1-plan.md#p1受入判定)。
P2ではDBの失効記録で許可したコンテナを回収し、作成台帳の完全IDが同じDocker daemonに存在しないことを保存できる。
作成未送信または不在確認済みの期限切れattemptを、最大3attempt・5秒と10秒のバックオフで再試行する。
2 Workerが取得競合した場合は、元の対象を再照合してから待機に戻り、次のrunを処理できる。
停止位置を変えた3ケースで、DB時刻による失効・回収・バックオフ後に別の常駐Workerが同じrunを再取得し、旧報告を拒否した。
[P2の受入条件と検証](design.md#2-workerの故障復旧試験)。
任意URL/コマンド/YAMLや非信頼コードの受付へ範囲を広げない。取得段階とnetwork noneの実行を分離する。
全P0〜P5のMVP受入条件と証拠が揃った時点で独立レビューと完成判定を提案し、発展課題へ自動的に進まない。

## P3の受入状況

1. 元bodyのHMAC、対象の検証、配送とrunの同時保存を[専用入口](webhook.md)に実装済み。
2. 署名付きのローカルHTTPSで同じ配送IDを10回再送してrunは1件。不正署名と同一IDへのbody変更を拒否し、受信プロセスやDBの再起動後に同じ配送を受理した。
3. 承認済みの公開HTTPS受信先が用意できたら、管理下リポジトリからpushを受信し、永続化して受信から10秒以内に応答することと、受付停止時のGitHub手動再送を確認する。
