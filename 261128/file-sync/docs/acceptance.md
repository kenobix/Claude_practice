# Phase 0〜5の受入条件

[元計画](../../../261014/plan_file_sync.md)の段階ごとに、実装前に期待値を固定する。本文のバイト列、サイズ、SHA-256および代表ケースの機械判読用の期待値は [expected.json](../fixtures/expected.json) にある。本文のSHA-256はPython標準ライブラリと `sha256sum` で照合した。revision・受理履歴・競合は [プロトコル](protocol.md) と [判定表・復旧手順](design.md) をもとに手で追った。製品の出力から期待値を更新すると、仕様違反を試験で見逃し得るため、期待値の変更時は契約の根拠を記録する。

## 試験の読み方

- 既定のパスは `notes.txt`。 `P` は `abc`、`Q` は `hello`、`R` は `world`、`S` はLF付きの `hello`、`E` は空ファイル。すべて [expected.json](../fixtures/expected.json) のバイト列とhashを照合する。`T` はtombstone（本文なし、`content_hash=null, size=0`）、`Ø` はローカル不存在またはハブ未登録（版0）。`F/2` は内容Fの版2を表し、クライアントの基準版は必要な箇所で別記する。
- `G` と `G2` は異なる世代。 `a1`、`a2`、`b2` 等は、AまたはBの操作IDを表す。試験ドライバでは数値末尾を32桁の16進に表し、同じ端末内で区別する。ハブの受理履歴を記すときは `a1@1` を操作a1、受理版1、結果 `applied` とする。no-opの受理は `unchanged` を明記する。初期に記載した履歴は末尾まで保持する。
- `基準S1` はハブ・A・Bが `P/1`、世代G、履歴 `[a1@1]`、blobはP、両端末の基準は1で競合・反映予定・送信待ちなし。 `空` は当該パス・blob・履歴なし、G。明記がなければ容量に余裕があり、ルート内は正常、認証済みで外部編集なし。書いていないパス、端末の基準版とファイル、世代、履歴、競合、削除退避は初期状態を維持する。保留はあとで再送・復旧・人の判断が必要な状態を指す。拒否されたPOSTに受理記録を作らない。
- 保持欄の値は初期ファイルだけでなく操作中の候補も検査し、残る場所を照合する。試験のために利用者が自分で削除した端末の内容は、既存のハブblobなど記載先で照合する。切断・停止点はイベントを観測して注入し、任意のsleepで発生を推定しない。
- Phase 0で実施するのは設計、固定値・依存関係・実行環境の確認。Phase 1〜5の行は後続の受入条件。最終受入では同じ対象SHAに、試験ID、注入点、ファイルとSHA-256、manifest、SQLite受理記録、端末状態を結びつける。拒否・保留が期待どおりの場合も合格とし、未実施は別に記録する。
