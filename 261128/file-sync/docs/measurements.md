# 初回同期の性能計測

## 再現

LinuxまたはWSL2のLinuxファイルシステムで、 `261128/file-sync` から実行する。Python 3の標準ライブラリと `findmnt` を使う。時間を記録する前に固定Goを使ってCLIをビルドする。 [Goと依存の再現](toolchain.md#goと依存の再現)

```bash
export GOTOOLCHAIN=local GOWORK=off CGO_ENABLED=1
go mod download all
go mod verify
result=$(mktemp -d)
python3 -B tools/verify_mvp.py measure \
  --product-sha 5534795714958e52e8c6f05fc9f7a4a740dabf89 \
  --trials 5 --output "$result/measurement.json"
```

1試行ずつハブとA・Bを初期化し、空のハブ、未登録の端末、人工ファイルを作る。Eは0バイト、Mは0値10,485,760バイト。各試行のあとで両端末とハブの本文、サイズ、SHA-256、基準版とハブの版1、パスごとの作成受理1件、競合・削除なしを照合する。A・Bとも生存パスをすべて確認する。検査は [固定fixture](../fixtures/expected.json) の値を使う。

## 計測区間

| 項目 | 開始から終了まで |
| --- | --- |
| Aの走査 | 単独の `scan` の呼び出しから終了まで。CLIプロセスの起動、ファイル読み取り、SHA-256、JSON出力を含む。 |
| Aの同期 | `register --seed` の呼び出しから終了まで。CLI起動、実際の走査・初回登録、PUT・changes、ローカル基準版確定を含む。 |
| Bの受信 | `register --pull` の呼び出しから終了まで。CLI起動、初回登録、manifest・GET、本文の反映と基準版確定を含む。 |
| 収束 | Aのseedの直前からBのpull終了までを連続して計測。AとBは順に実行し、その間に待機時間を設けていない。試行のハブ起動と準備待ち、ファイル生成、状態の初期化、単独の `scan`、終了後の照合は含めない。 |

Pythonの単調増加時計 `time.perf_counter_ns()` で測り、JSONにはナノ秒の整数を収録した。表ではナノ秒からミリ秒へ換算し、小数第1位に丸めた。

通信はIPv4のlocalhost、HTTPで行った。Python標準ライブラリのローカル中継はリクエストを1件ずつGoハブへ渡し、実際に読み取った要求・応答の本文長と要求数をエンドポイント別に加算する。この中継は本文をメモリに読み、HTTPヘッダーを付けて転送する。中継の時間もAの同期、Bの受信、収束に含まれる。本文量にはTCP・HTTPヘッダーを含めず、クライアントと中継の境界で1回だけ数えた。PUT本文はAからのblob、GET応答本文はBが受け取るblobに当たる。PUTのJSON応答、manifestとchangesのJSONも別の項目として計上した。

保存量はB終了直後、ハブの停止・読取専用SQLでの照合より前に測った。DB本体、WAL、SHMとblobの論理ファイル長を別に記録した。物理ディスク使用量、SQLite外の管理ファイル、ファイルシステムの管理領域はこの値に含まない。 [Phase 4の障害時・上限時の観測](phase4-verification.md#固定容量とsqliteの論理長)

## 実測環境と結果

計測日は2026-11-28（JST）。対象は製品コードSHA `5534795714958e52e8c6f05fc9f7a4a740dabf89`。 Go 1.27.4、Cgo有効、GCC 13.3.0、`mattn/go-sqlite3 v1.14.52` 同梱SQLite 3.53.4、`golang.org/x/sys v0.45.0`、Python 3.12.3を使用した。

Ubuntu 24.04.4 LTS、WSL2のLinux 6.6.87.2-microsoft-standard-WSL2、x86-64、ext4で計測した。CPUはAMD Ryzen 7 7735HS with Radeon Graphics、WSL内の論理CPUは8、メモリは29,429,559,296バイト（約27.4 GiB）。CPU名は同じ環境の `lscpu` と `/proc/cpuinfo` で補記した。

### HTTPと保存量

HTTPの各値は同じ条件の5回すべてで一致した。保存量は5回の範囲を示し、サイズはバイトで記載する。

| 試料 | PUT回数 / 要求本文 | GET回数 / 応答本文 | DB本体 | WAL | SHM | blob数 / 論理長 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 空ファイル100件 | 100 / 0 | 100 / 0 | 163,840 | 16,512 | 32,768 | 1 / 0 |
| 空ファイル1,000件 | 1,000 / 0 | 1,000 / 0 | 1,142,784–1,146,880 | 16,512 | 32,768 | 1 / 0 |
| 10 MiBファイル1件 | 1 / 10,485,760 | 1 / 10,485,760 | 53,248 | 16,512 | 32,768 | 1 / 10,485,760 |

この計測の空ファイルは各条件で実体が1件にまとまった。AとBは各パスについてPUTとGETを1回ずつ行った。manifestは各試行で2要求、changesはパス数と同数。JSONの `http` に各要求・応答の本文サイズを収録した。

## 読み方と限界

空ファイルと10 MiBファイルでは処理負荷の内訳が異なる。空ファイルの測定は本文を送らなくても発生する各パスの登録、作成、DB処理を含む。10 MiBの測定では一つのパスについて、全量の送受信・読み取り・SHA-256・同期が発生する。ハブに共有blobが1件あっても、要求回数はクライアントの送受信の実測値で確かめる。

ウォームアップ用の試行は設けなかった。各試行の領域は新しく、同じOS上でファイルを用意して単独の `scan` を先に行った。OSのキャッシュは無効化していない。実測には中継・プロセス起動・WSL2の仮想化やストレージの影響が含まれる。インターネットや別マシンを経由する性能、稼働中の変更の速度、長時間運転時の性能はこの値から推定しない。各条件5回の中央値と範囲を示し、p95は集計していない。性能の数値は合否に使わない。
