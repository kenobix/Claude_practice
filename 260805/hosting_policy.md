# ホスティング方針（GitHub Pages / Netlify / Vercel）

このドキュメントは、リポジトリ内で公開しているページ・アプリについて「GitHub Pagesのままでよいか、Netlify/Vercelへ作り直す・修正すべきか」の調査結果と方針をまとめたものです。判断基準そのものは [../CLAUDE.md](../CLAUDE.md) を参照してください。

## 要約

以前、別の会話（本ドキュメント作成の参考として提示されたもの）では「`260427`・`260701`でGemini APIキーをフロントエンドに埋め込まざるを得ず、GitHub Pagesの構造的限界からVercelへの移行が必要」という前提で助言がされていました。しかし今回リポジトリを実際に調査した結果、**この前提は現状のリポジトリには当てはまりません**。

- `260427`（OpenClaw/Ollama構築の記録）と `260701`（AI箱庭シミュレーション）は、どちらもGitHub Pagesで公開されていません。前者はドキュメントのみ、後者はローカルで動かすPythonシミュレータ＋分析スクリプトです。
- 実際にGitHub Pagesで公開されているのは以下の5件のみ（`README.md`のPages一覧表より）:
  - ルート `index.html`（トップページ）
  - `260502`（デザインキット: ポートフォリオ・提案デッキ・ワンページャー・紹介アニメーション）
  - `260510/01_linux_permissions`（Linux権限ハッキングラボ）
  - `260521`（OpenAI/Geminiチャットアプリ）
  - `260630`（システムプロンプト注入チャットアプリ）
- このうち外部APIを呼ぶのは `260521` と `260630` のみですが、どちらも**APIキーをコードに埋め込んでいません**。ユーザーがUI上で自分のAPIキーを入力し、ブラウザの `localStorage` にのみ保存、そこから直接プロバイダのAPIへ送信する「BYOK（Bring Your Own Key）」方式です。リポジトリ・GitHubリポジトリ上に秘匿すべきシークレットは存在しません（`git log`でも過去に鍵がコミットされた形跡なし）。

したがって、**現時点で緊急に移行が必要なページはありません**。ただし将来的な設計変更の判断材料として、以下に詳細を残します。

## 現状の公開ページ評価

| ページ | 種別 | 外部API呼び出し | 秘密情報の露出リスク | 判定 |
|---|---|---|---|---|
| ルート `index.html` | 静的HTML/CSS | なし | なし | GitHub Pages維持 |
| `260502`（デザインキット） | 静的HTML/CSS/JS | なし | なし | GitHub Pages維持 |
| `260510/01_linux_permissions` | 静的HTML/JS（模擬ターミナル） | なし（表示内容はすべてダミー） | なし | GitHub Pages維持 |

## プロジェクトごとの方針

### 移行不要・GitHub Pages恒久維持

- **ルート `index.html` / `260502` / `260510`**: 完全に静的で外部API呼び出しがない。GitHub Pagesの無料・無制限・追加設定不要というメリットをそのまま享受できる。移行する理由がない。

### 現状維持だが、将来の設計変更時にVercelを検討

- **`260521`・`260630`（BYOKチャットアプリ）**: リポジトリ側に秘密情報はなく、現状は「自分のキーを持っている人だけが使う個人用デモ」として問題ない。
  - **将来オプション**: もし「APIキーを持たない第三者にもそのまま触ってもらえる公開デモ」にしたい場合は、Vercelへ移行し以下の構成に変更する。
    - Vercel Serverless Function（例: `/api/chat`）でGemini API呼び出しをプロキシし、APIキーはVercelの環境変数として保管（クライアントに一切渡さない）。
    - 誰でも使える共有キーになるため、簡易レート制限（IPベース、または1日あたりの呼び出し回数上限）を関数側に実装し、キーの濫用・高額請求を防ぐ。
    - `260630`のシステムプロンプトも同じ関数内に留めることで、ソース表示による閲覧を防げる。
  - 現時点ではこのオプションを実施する必要はない。BYOK方式のまま使い続けるならGitHub Pages維持でよい。

- **`260701/map_view_google.html`**: 現状GitHub Pagesで公開されていない（Python製シミュレータのローカル成果物）。Google Maps JavaScript APIキーもBYOK方式（UI入力→`localStorage`）。将来これを公開する場合は、260521/260630と同じ将来オプション（Vercelサーバーレス関数によるプロキシ化）を検討する。現時点でアクションは不要。

### 公開する場合はVercel（＋別途バックエンド）が必須

- **`260406`（個人開発管理ダッシュボード: React + Hono + SQLite）**: 現状はローカル/LAN限定運用（Windows `netsh portproxy`経由でのスマホアクセスのみ）で、GitHub Pagesには公開されていない。
  - GitHub Pagesは静的ファイルしか配信できないため、Honoバックエンド・SQLiteを含むこの構成はそのままでは載せられない。
  - 将来インターネット公開する場合は、フロントエンドをVercelにデプロイし、HonoのAPIをVercel Serverless Functions（Honoは`hono/vercel`アダプタでそのままFunctions化可能）として動かす。SQLite（ローカルファイルDB）はサーバーレス環境と相性が悪いため、Turso・Neonなどのホスト型DBへの移行も併せて必要になる。
  - 現時点で公開予定はないため、これは「公開を決めた時点で必要になる設計変更」として記録するのみ。

- **`260525`（RAG学習）**: 自身のwork_log内で「GitHub Pages制約: 静的サイトではサーバーサイド処理が動かない」とすでに自己診断済み。将来Webアプリ化する場合は `260406` と同様、Vercel（サーバーレス関数でRAGのチャンク検索・生成処理を実行）を検討する。現時点でWeb化の計画はない。

## 判断基準の再掲（詳細）

| 条件 | 選択 | 理由 |
|---|---|---|
| 完全静的・秘密情報なし | GitHub Pages | 無料・無制限・追加設定不要。このリポジトリの既定。 |
| サーバーレス関数が必要／APIキーやプロンプトを秘匿したい／Next.js等SSR | Vercel | Reactスタック中心のこのリポジトリと相性が良く、プレビューデプロイの完成度が高い。Netlifyより優先。 |
| Vercel固有機能を避けたい／Netlify独自機能（フォーム等）を使いたい静的寄り案件 | Netlify | Vercelとほぼ同等の代替。無料枠・使いやすさに大差はない。 |

Vercel/Netlifyとも、CLI初回の `login` のみブラウザ認証が必要で、以降のデプロイ・環境変数管理はBashから非対話的に実行できる（詳細は [../CLAUDE.md](../CLAUDE.md) 参照）。

## スコープ外

本ドキュメントは方針決定のみを目的としている。実際のVercel/Netlifyプロジェクト作成、CLIログイン、`vercel.json`/`netlify.toml`の作成、環境変数の設定といった実装作業は含まない。将来オプションを実施する際は、別途タスクとして着手すること。

## 追加の考察

移行してから見直しを行うのではなく、次にホスティングを判断する場面で参照できるよう、調査時に浮かんだ追加の論点を残しておく。

### 1. Vercel移行を待たずにできる低コストな改善（`?key=`クエリパラメータ問題）

`260521/gemini.html`・`260630`はGemini APIキーをURLのクエリパラメータ（`?key=...`）で渡している。これはリファラヘッダーやサーバーアクセスログにキーが残る経路になり得る、BYOK方式の中でも比較的リスクが高い実装。

Gemini APIは `x-goog-api-key` **HTTPヘッダー**でのキー送信にも対応している。クエリパラメータをヘッダーに置き換えるだけで、Vercelへの移行やサーバーレス関数を用意することなく、この経路のリスクを下げられる。ホスティング先の変更を伴わない改善なので、次にこの2つのファイルを触る機会があれば併せて直しておくとよい（`260521/index.html`のOpenAI版はすでに`Authorization`ヘッダー方式なので対象外）。

### 2. 将来Vercelへ移行する場合のコスト面の留意点

GitHub Pagesは帯域・リクエスト数の実質無制限（緩やかな公平利用ポリシーのみ）だが、VercelのServerless Functionsは無料枠でも**関数の実行回数・実行時間に上限**がある（Hobbyプランは月100GB帯域＋関数実行に一定の上限）。個人の学習用デモ程度のアクセス量なら無料枠内に収まる想定だが、`260521`/`260630`を「無キーで誰でも試せる公開デモ」にしてSNS等で拡散された場合、無料枠超過や共有APIキーの濫用によるGemini側の課金リスクが発生し得る。移行する際はレート制限に加えて、Vercel側の使用量アラート設定も合わせて検討する。

### 3. 本ドキュメントの見直しタイミング

以下のいずれかに該当したら、本ドキュメントと`CLAUDE.md`の判断基準を再確認し、必要なら更新する。

- 新しい日付ディレクトリで、フロントエンドからAPIキーやプロンプトなどの秘密情報を扱うページを追加したとき。
- `260521`/`260630`/`260701`のいずれかを「無キーで使える公開デモ」に変更すると決めたとき（Vercel移行オプションの実施タイミング）。
- `260406`（ダッシュボード）や`260525`（RAG）をインターネット公開すると決めたとき。
- ルートの`README.md`のGitHub Pages一覧を更新したとき（新規公開ページの判定をこの基準に沿って行ったか確認する）。
