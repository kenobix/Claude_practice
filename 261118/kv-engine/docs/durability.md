# 耐久性・ロック・復旧 v1（段階2実装）

## 対象環境と保証の条件

LinuxまたはWSL2上の、ローカルのext4ファイルシステムを対象とする。観測環境は[README](../../README.md)に記載した。
Windowsマウント（/mnt/c等）、ネットワークFS、他OSは今回の保証対象外。
WSL2ではext4の背後に仮想ディスク・Windowsホスト・実ストレージがある。
GoのFile.Sync成功だけで、この全層の電源断耐性を実証したことにはならない。

成功応答済みの更新が復旧後も残ることを目標とする。前提は、OS・仮想化層・装置が同期契約を守り、その後に破損や外部からの変更がないこと。
fsyncエラー、ディレクトリ同期の未対応、読み取りエラーはいずれも無視しない。
媒体故障、bit rot、悪意のある変更、メモリ破壊、他プロセスからの直接編集は保証外。
[限定条件の性能計測](measurement.md)は実施済み。電源断耐性は未検証。kill -9試験はプロセス障害の検証に限る。

## ファイルとOSロック

DBディレクトリは利用者が事前に作成する（専用領域、同一ユーザー、起動中にディレクトリや内容を外部から置換しない）。
Openとinspectは指定されたパスをそのままLinuxに渡し、探索権限やsymlinkを含む `..` の解決に従う。
取得したディレクトリFDを基点に、LOCKとdata.logを開く。
`LOCK` をO_CREATE|O_RDWRで開き、Linuxの `syscall.Flock(fd, LOCK_EX|LOCK_NB)` で排他ロックを取得する。
ファイルの有無だけでロックの所有を判定しない。getとinspectでも排他ロックを取得し、競合したら直ちにErrLockedを返す。
DBが開いている間はLOCKのFDを保持する。LOCKはunlinkも置換もしない。全FDを閉じるとOSがロックを解放する。
flockはadvisoryなので協調しない外部writerを防げない。
Go標準ライブラリのLinux用実装を選び、他OS対応は将来の判断にする。

## 新規作成と更新の順序

1. 引数を検証し、既存DBディレクトリのLOCKを取得する。
2. 新規DBの場合はdata.logをO_CREATE|O_EXCLで作る（0600）。16バイトのヘッダーをすべて書き込んでからFile.Syncを呼ぶ。
3. DBディレクトリを開いてSyncし、LOCKとdata.logのディレクトリエントリを同期する。
   DBディレクトリ自体の永続性にはその親のSyncも必要なので、初回作成時はその親もSyncする。
   取得したディレクトリFDを基準に、それぞれ `.` と `..` を開いてDBディレクトリとその親を同期する。
   入力が相対パス、末尾スラッシュ付き、symlink経由の場合も、ロックと同期は実際に開いたDBディレクトリを基準にする。
   DBディレクトリまたはその親のSyncに失敗した場合、Openは失敗し、更新の成功応答を返さない。
   さらに上の新規ディレクトリ階層は利用者が事前に作成・永続化済みであることを前提とする。
   起動途中で失敗した既存ファイルは削除せず診断する。
4. 既存ログなら復旧検証を終える。既存の場合もDBディレクトリと親のSyncを完了してから更新を許可する。
5. mutexを保持した状態で各更新を検証し、容量とsequenceを確認する。レコード全体をメモリ上で組み立てる。
6. ログ末尾にレコードの全バイトを書き込む。一部だけ書けた場合は残りを書き込み、0バイトかつnilならio.ErrShortWriteとして停止する。
   一部を書き込んだ後にエラーが返った場合も成功として扱わず、そのプロセスで開いているDBを失敗状態にする。
7. data.logのFile.Syncが成功してからメモリ索引と最新sequenceを更新する。
8. エンジンは同期済みのsequenceを返す。CLIはCloseが成功してから標準出力に成功応答を書く。短い出力もI/Oエラーとして扱う。

ログのサイズを伸ばす通常追記はファイル同期を行う。新しい名前や置換を作らないので、毎操作の親Syncは不要。
DBハンドルの生存中はGET・更新・Inspect・Closeを直列化。複数操作のトランザクションは提供しない。

## 失敗状態

write / Sync / 読み取りI/Oエラーを検出したDBは失敗状態となり、Close以外の操作をErrRecoveryRequiredで拒否する。
I/O結果が不明なまま同じプロセスで追記を継続しない。Closeで資源を解放し、Openで再検証する。
入力・上限・ロック競合はI/O失敗状態にしない。初期化・復旧失敗のOpenはDBを返さない。
Syncが成功した後、応答する前に停止した場合や、標準出力への書き込みが失敗した場合は、成功応答を受け取れなくても更新が残ることがある。
再試行の重複排除は提供しない。存在しないキーをDeleteした場合も新しいsequenceを割り当てる。
[CLI応答境界試験](cli-response-experiments.md)ではCloseの前後、出力途中、全バイトの出力後に停止させ、同期済みの更新が残ることを確認した。
完全な応答の受信とexit 0の確認は区別し、プロセス異常終了を通常の成功と扱わない。

## 復旧とinspect

ロック取得後に先頭から検証し、検証済みPUT/DELETEだけでメモリ索引を再構築する。
正常なEOFに達した場合はそのまま開く。問題が不完全な最終レコードだけの場合は、元のサイズ、最後に検証できた境界、理由を診断として出力する。
診断出力が完了したらTruncate(last_valid_offset)、data.log.Syncの順に実行し、両方が成功してからDBを開く。失敗した場合は通常起動を止める。
全バイトを読めたレコードのCRC不一致、不正なヘッダーやsequence、未知の形式、途中の破損を検出した場合は、ログを変更せず起動を止める。
初回の短いファイルヘッダーも自動修復しない。利用者の既存データを削除しない。
修復ツールは今回対象外。将来必要なら明示的に作ったコピーだけを扱う。
inspectは同じ検証をするが切り戻さない。開くだけで診断対象を失わないようにする。

## 判断の根拠

- [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html): ファイル同期とディレクトリエントリの同期は別。
- [Linux flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html): advisory lock、非待機取得、FDの生存期間。
- [Go os.File.Sync](https://pkg.go.dev/os#File.Sync): ファイル内容のstable storageへのcommitを要求するAPI。

上記は設計の根拠。同期呼び出し順序とロック競合はテストしたが、装置の電源断保証の実測ではない。

## 段階2の実装上の補足

- 排他ロックとmutexを保持し、検証済みの末尾offsetへWriteAtで追記する。O_APPENDは使わない。
  書き込むのは常に末尾だけで、短いwriteを補完し、0バイトwriteや一部成功+errorは失敗状態にする。
- data.log新規作成はO_EXCL。既存ファイルにはTRUNCを使わず、LOCKはunlinkしない。
  data.log/LOCKのsymlinkと非regular fileは拒否。新規ログ作成先はLOCK以外に項目のない既存ディレクトリ。
- ログ走査はStatで得た最大256 MiBのsnapshotに制限する。短いfile headerは起動拒否。
  正常に検証できた範囲の直後で実際のファイル末尾に達したときだけ、短いレコードヘッダー、またはヘッダー検証済みで本文が短いレコードを修復する。
  観測サイズが16バイト以上あるのにファイルヘッダーの読み取り中にEOFに達した場合も含め、
  観測した終端より前に読み取りが途絶えた場合はI/Oエラーとし、復旧しない。
- 復旧前に `tail_truncate_planned` とold_size/last_valid_offset/reasonを診断出力する。
  LFを含むイベント全体のwrite完了を検査し、短いwrite/nilも失敗とする。全長受理後のerrorも無視しない。
  診断失敗ではファイルを変更しない。Truncate/Sync失敗ではDBを返さずロックを解放する。
  [診断完了条件の試験](recovery-diagnostics.md)で、切り戻し・ログSync非実行と全バイト不変を検証した。
- inspectはログをO_RDONLYで開き、修復・Syncをしない。LOCKは作成する場合がある。
- 起動失敗時のFD、Close時のログ→LOCKの順を保つ。既存データを初期化し直さない。
- Getでread/CRCエラーを検出した場合もDBを失敗状態にし、Close以外を拒否する。

この限定的な末尾復旧は、当時の依頼に従って段階3の予定から前倒しで実装した。
任意の外部truncateと追記中断は常に識別できない。協調しない外部編集や保存装置の故障は依然保証外。
段階2ではkillを行わず、段階3の初回単位で既存DB更新の停止点と応答履歴を使うSIGKILL試験を追加した。
[更新停止の実験](crash-experiments.md)に加え、[Open中の停止試験](open-crash-experiments.md)で初回作成9点と復旧4点を検証した。
0/8バイトの既存headerは破損として不変のまま拒否し、完全headerは空DBとして再開。
復旧中断後も成功応答済みの正常prefixを保ち、二度目のOpenで不要な修復を行わないことを確認。
[複数seedの更新停止試験](seeded-crash-experiments.md)では3 seed・48停止ケースと正常終了6ケースで成功応答履歴を照合した。
[複合I/O試験](compound-io-experiments.md)で更新失敗と再Open失敗の30組合せ、および対照を検証した。
復旧Sync失敗時はTruncate済みでもOpenを失敗させる。注入を除いた再試行で正常prefixを再生できたが、
これは失敗したSyncの電源断時保証ではない。
[Close競合試験](close-concurrency.md)ではI/O先行・Close先行・同時開始の18ケースを検証した。
Closeは進行中I/Oを待ち、data.log→LOCKの順で閉じる。Closeが先に進むと他のAPIはErrClosedとなる。
最初のCloseだけが閉鎖エラーを返し、同時/繰返しCloseはnilとなる。
製品CLI応答周辺は[後続試験](cli-response-experiments.md)で検証済み。
ホスト停止・電源断・診断出力先の永続化は未検証。
