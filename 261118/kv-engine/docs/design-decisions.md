# 実装の読み順・設計判断・振り返り

## 読む順序

1. [API/CLI契約](api.md)と[形式v1](file-format.md): 入力、成功/失敗、sequenceとCRC、EOFの分類。
2. [record.go](../internal/record/record.go): 入力検証→encode、固定header検証→長さ検証→本文確保→CRC。
3. [scan.go](../internal/recovery/scan.go)では、観測時のログサイズを上限に先頭から検証し、正常と確認できた範囲だけを位置索引に反映する。
4. [disk_linux.go](../internal/engine/disk_linux.go): LOCK→初期化/Sync→走査→限定末尾復旧、追記→Sync→索引公開、Get/Close。
5. [persistent_linux.go](../cmd/kv/persistent_linux.go): 入力を検証し、更新/読取→Close→stdout。成功応答とexitを確認。
6. [公開fixture検証](../tests/fixtures_test.go)、[受入対応表](stage3-acceptance.md)、[デモ](demo.md)、[計測](measurement.md): 仕様のバイト例から実プロセスと観測へ進む。

## 選択とトレードオフ

| 判断 | 採用した理由と代償 | 根拠/後回しにしたもの |
|---|---|---|
| 全件走査とメモリ索引 | 起動時は全レコードを検証するためログ長に応じて時間がかかる。稼働中はkey→最新レコード位置だけを保持し、GET時に値とCRCを再読取する | [実測](measurement.md)はwarm OpenとGoヒープ差分を測る。B+Tree等の永続索引は追加しない。古いレコードも走査し、上書きだけでログが縮むわけではない |
| 毎回同期とまとめて同期 | PUT・DELETEごとに、エンジンは全バイトの書き込み、File.Sync、索引の更新の順に処理してから成功を返す。呼び出し側はどこまで完了したかを判断できる一方、更新のたびに同期を待つ | [同期順序](durability.md)と[応答境界](cli-response-experiments.md)。まとめて同期するバッチやトランザクションは未実装で、性能は比較していない |
| 破損時停止と自動修復 | 全バイトを読めても検証に通らないレコードや、ログ途中の破損を検出した場合は停止する。後続レコードは勝手に採用しない。追記中断モデルに合う不完全な末尾に限り、診断の全バイトが受理されてからTruncate、Syncの順に進む | [復旧診断](recovery-diagnostics.md)。任意の外部truncateを追記中断と識別できる保証はない。汎用の修復や重要データへの利用は想定しない |

初回はログファイル名とDBディレクトリ名を永続化するため、DBディレクトリとその親のSyncも必要とする。これらの同期に失敗するとOpenは成功しない。
CLIはCloseが成功してから応答を出力する。同期済みの操作は、Closeや応答の出力が失敗した場合でもログに残ることがある。
完全な応答と通常終了を確認できなければ、更新が残っていないと仮定せず読み直す。再試行の重複排除は提供しない。

## 守る範囲と既知の制限

Linuxローカルext4、協調する単一writer、UTF-8キー1〜256 B（NUL不可）、値0〜1 MiB、ログ上限256 MiB。
APIはinternalパッケージであり、外部利用者向けライブラリとしての公開/互換性管理は対象外。
メモリモードは終了すると消える。永続モードでもOS/仮想化/装置が同期契約を守る前提がある。
SQL、MVCC、複数writer、ネットワーク、コンパクション、複数操作トランザクションを追加しない。
容量上限に達したら明示エラー。利用者データを自動削除したり、破損を黙って飛ばしたりしない。

電源断、ホスト/カーネル停止、実媒体障害、WSL/装置flush、診断先の永続化は未検証。
[計測](measurement.md)はwarm再Open・同期PUT・Goヒープの単一環境の観測で、cold start/RSS/他環境比較ではない。
CRCは偶発的な破損検出で、暗号的な改ざん防御ではない。全故障/全seed/全並行スケジュールの証明もしない。

## 振り返りと最終レビューで確かめること

- 復旧結果を成功応答列だけと完全一致させると、同期後・応答前の正常な残存を誤って失敗とする。
  親に保持したack列と最大1件の未応答操作を分けることで、部分値や成功喪失を検出できた。
- 書き込みが途中で終わっていないかは、ログ、CLI応答、復旧前の診断出力のいずれでも確認する必要があった。
  診断出力の全バイトが受理されても、診断先のfsyncは確認できない。
- SIGKILLでOSキャッシュは消えない。Sync前の完全レコードが残った観測を、電源断保証や常時残存に一般化しない。
- warm OpenとGoヒープという測定区間/指標を明示した。同期を省いた速度との比較で保存保証を曖昧にしない。
