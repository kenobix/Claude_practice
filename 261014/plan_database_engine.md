# 永続KVから作るデータベースエンジンの詳細計画

- 作成・資料確認日: 2026-10-14
- 状態: 企画・作業計画。以下の機能、検証、計測は未実施。
- 関連: [企画全体の比較と選び方](next_project_plan.md)
- 想定: 個人開発、LinuxまたはWSLのLinuxファイルシステム、ローカル実行。

## 1. 目的と企画の修正判断

ファイルへの書き込みが、どの時点で「保存できた」と言えるのかを自分で設計し、プロセス停止後の復旧で確かめる。対象利用者は、ストレージの仕組みを学びたい開発者と、設計・実験を評価するレビュー担当者とする。

元案の自作DBは目的に合う。ただしSQL解析、B+Tree、トランザクション、MVCCを同時に完成させる計画は広すぎる。最初の完成品は、単一writerの永続Key-Valueストアと復旧実験に絞る。SQLや高度な同時実行は完成後の選択肢とする。

既存の[ダッシュボードのDB初期化](../260406/dashboard/backend/src/db/index.ts)には、`better-sqlite3`とWALモードの利用がある。[README](../260406/dashboard/README.md)にもORMとSQLiteの構成が記録されている。今回新たに取り組むのは、ログ形式、永続化の順序、復旧器を実装する部分である。確認した主要コード・ログに同種の自作エンジンは見当たらなかったが、全ファイルの未実装を証明した判断ではない。

企業への説明材料は「DBを作った」という名称だけでは足りない。成功応答と永続化の関係、破損を検出したときの動作、速度と保存保証の関係を、実験記録から説明できることを成果にする。バックエンドやストレージ分野への関心を示しやすい企画だが、採用評価を保証するものではない。

本人は広いソフトウェア開発力とAI・MLエンジニアの両方を重視し、数か月以上の深掘りも可能と回答している。本案は永続化の基礎を深める独立候補であり、MLOpsやCIの着手条件ではない。AI・MLの実績との接続を強める場合は、完成後に実験メタデータの保存例を添える。ただし学習用DBへ重要な実験記録を移行することは前提にしない。

## 2. 最小完成範囲と後回しにする機能

| 項目 | 最初の完成範囲 |
|---|---|
| 操作 | `put`、`get`、`delete`、`inspect`、再起動時の復旧 |
| データ | UTF-8キーは1〜256バイト、値は任意バイト列で0〜1 MiB。不存在と空値を区別 |
| 永続化 | 追記ログ1本、各更新を同期してから成功応答、起動時に索引を再構築 |
| 同時実行 | 1プロセス、操作を直列化。DBディレクトリをOSの排他ロックで保護 |
| 破損時 | 不完全な末尾と検証不能な破損を区別し、理由・位置を報告 |
| 操作面 | CLIとライブラリAPI、人工データを使った再現用デモ |
| 制限 | ログ上限は暫定256 MiB。到達時は明示エラーにして容量管理を後回しにしない |

SQL、B+Tree、MVCC、複数writer、ネットワークAPI、レプリケーション、圧縮、自動コンパクション、Web UIは最初の完成条件に含めない。MVPは単一操作の原子性を扱い、複数操作のトランザクションや一般的な「ACID完全対応」を標榜しない。

## 3. 暫定スタックと構成

Goを暫定候補とする。ファイルI/O、バイナリ形式、エラー処理を追いやすく、配布用CLIを作りやすいことが理由である。着手時に本人の言語経験を確認し、Rustを選ぶ場合は所有権・I/O周りの学習時間を別に見積もる。

```text
CLI / library API
      ↓ 操作を直列化
engine ── メモリ索引（key → 最新レコードの位置）
      ↓
record encoder → append log → file sync → 成功応答
      ↑
起動時の decoder / recovery / inspect
```

自作するのはレコード形式、追記処理、索引更新、復旧規則、障害注入点である。ファイル操作、CRC、バイナリ変換、CLIの引数処理、OSロックには標準ライブラリや十分に利用されている実装を使う。MVPの保存先としてSQLiteや既存KVを呼び出す構成にはしない。

コードの置き場所は着手日ディレクトリの`kv-engine/`とし、`cmd/`、`internal/record/`、`internal/engine/`、`internal/recovery/`、`docs/`に分ける。実際のGoバージョンと依存バージョンは着手時に固定して記録する。

## 4. データ契約と守る性質

### 4.1 ログ形式

ファイル先頭にmagic、形式バージョン、予約領域を置く。各レコードは固定長ヘッダー（長さ、単調増加するsequence、操作種別、キー長、値長、ヘッダーCRC）と、キー、値、レコードCRCを持つ。長さを含むヘッダーを先に検証し、長さの破損を単なる未完の末尾と誤認しない。バイト順、CRCの対象範囲、最大レコード長、DELETEの値長ゼロを`docs/file-format.md`で確定する。

長さを検証する前に入力サイズ相当のメモリを確保しない。未知のバージョン、不正な操作種別、不正な長さ、sequenceの逆行は明示エラーとする。CRCは偶発的な破損検出に使い、改ざん防止用の暗号署名とは扱わない。

### 4.2 更新の順序と成功応答

1. 入力・容量・ロック状態を検証し、レコード全体を組み立てる。
2. 短いwriteを考慮して全バイトを書き込み、ファイルの同期処理を完了させる。
3. 初回ファイル作成では、親ディレクトリの同期も成功応答前に完了させる。
4. メモリ索引を更新し、操作番号を含む成功応答を返す。

I/Oエラーや同期失敗の後は、そのプロセスで新たな更新を受け付けず、復旧が必要な状態として閉じる。「エラーだったのでディスクに何も残っていない」とは仮定しない。SQLiteの原子的コミットの説明も、ディスク・OSへの前提と書き込み順序を明示している。[SQLite: Atomic Commit](https://www.sqlite.org/atomiccommit.html)

### 4.3 復旧と保証の境界

- 起動時はロック取得後、先頭から検証済みレコードを再生し、最後の値と削除状態を復元する。
- EOFで終わる不完全な最終レコードは、最後に検証できた境界まで切り戻して同期する。処置前の情報を診断ログに残す。
- 全長があるレコードのCRC不一致や途中の破損は、自動で飛ばしたり切り捨てたりせず、通常起動を止める。修復はコピーを対象にした別操作とする。
- 成功応答済みの更新は、OSと保存装置が同期契約を守る前提で復旧後も残ることを目標とする。
- 同期完了後・応答前に停止した操作は、呼び出し元が成功を受け取っていなくても復旧後に現れ得る。
- 検証器は成功応答済みの操作列と、停止時に未応答だった最大1操作を分ける。成功応答列だけとの完全一致を要求せず、最後の未応答操作が全体として残る場合も許容する。
- 最小構成は直列操作なので、復旧結果は完了したレコード列の一部までとなる。途中のPUTの値を混ぜない。
- `kill -9`はプロセス障害の実験であり、実機の電源断や保存装置の故障に対する証明とはしない。

ファイル同期とディレクトリエントリの同期は別に扱う必要がある。実装対象OSの挙動は[Linux `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html)に照らして記録する。

## 5. 段階別の作業計画

### 段階0: 操作と失敗の仕様を確定する（8〜12時間）

- PUT上書き、存在しないキーのDELETE、空値、上限超過、ロック競合の応答を決める。
- ファイル形式の例を手書きし、正常ログ、不完全な末尾、破損ログの例を作る。
- OS・ファイルシステム・同期前提、対象外の障害を`docs/durability.md`に記載する。
- 成果物: API仕様、形式仕様、障害一覧、設計判断メモ。
- 完了条件: 別の人が仕様だけを読んで各入力の結果と復旧方針を判断できる。

### 段階1: メモリ版とレコード処理を作る（14〜22時間）

- CLIからPUT・GET・DELETEを使えるメモリ版を作る。
- レコードのencode/decodeを分離し、境界値、切れた入力、不正な長さを扱う。
- 正解の参照モデルを単純な辞書として定義し、以後の結果照合に使う。
- 成果物: CLI、レコード処理、仕様と対応する検証ケース。
- 完了条件: キー不存在、空値、上書き、削除が区別でき、不正入力でpanicや過大確保を起こさない。

### 段階2: 永続化の縦切りを完成させる（20〜30時間）

- 排他ロックを追加し、追記・同期・索引更新・成功応答を実装する。
- 起動時にログを再生し、ファイル位置を使ったGETを実装する。
- 書き込み上限、ログ増加量、I/O失敗の診断を追加する。
- 成果物: 再起動しても値が残るCLI、初回起動とロック競合の手順。
- 完了条件: 混在したPUT・DELETE列が通常再起動後に参照モデルと一致し、2プロセス目が安全に拒否される。

### 段階3: 復旧と障害実験を完成させる（24〜38時間）

- 各write前後、同期前後、応答直前に停止させる障害注入点を設ける。
- 不完全な末尾の復旧と、途中破損の停止を実装する。
- writeの一部成功、ディスク容量不足、同期失敗をI/O抽象層で再現する。
- 成果物: 自動再現できる障害ケース、応答履歴と復旧結果の照合表。
- 完了条件: 成功応答済み操作を失わず、未応答操作の許容結果を仕様どおり説明できる。これは定義した故障モデル内の条件とする。

### 段階4: 調査用CLIと計測を整える（14〜22時間）

- `inspect`でレコード数、最新sequence、削除数、ログサイズ、検証不能位置を表示する。
- ランダム操作列を固定seedで生成し、復旧後の内容を参照モデルと照合する。
- 1千・1万・10万キーなど、容量上限内で起動時間、更新待ち時間、メモリ量を測る。
- 成果物: 機械可読な計測結果、実行条件、ログを説明する小さな図。
- 完了条件: CPU・保存先・同期条件・値サイズ・件数を揃えて結果を再現できる。

### 段階5: 第三者が試せる成果物にする（12〜20時間）

- 人工データを使った正常系と復旧系のデモを用意する。
- 使い方、実装の読み順、保証する範囲、既知の制限をREADMEへ整理する。
- 設計判断を「全件走査対メモリ索引」「毎回同期対まとめて同期」「破損時停止対自動修復」で説明する。
- 成果物: ソース、起動手順、3〜5分のデモ、障害実験表、振り返り。
- 完了条件: クリーンな環境で正常操作と停止・復旧を再現でき、本人が書き込み順を説明できる。

## 6. 実装時に行う検証・実験

| ケース | 観測する結果 |
|---|---|
| PUT→上書き→DELETE→再PUT | 再起動後に最後の状態と値が一致する |
| レコードの各位置で書き込み中断 | 不完全なら直前まで、完全なら当該を含み得る。値の一部は見えない |
| 同期後・応答前で停止 | 応答なしでも操作が残る可能性を正しく報告する |
| 途中の1バイト改変 | CRC不一致位置を報告し、後続を黙って採用しない |
| ディスク容量不足・同期失敗 | 成功と報告せず、後続更新を止め、再起動後に状態を確認できる |
| 2プロセス同時起動 | 片方だけが開ける。ロックファイルの存在だけを所有判定にしない |
| decoderへのランダム入力 | panic、範囲外アクセス、過大なメモリ確保を起こさない |
| 同じ操作列を複数seedで再生 | 参照モデルと値・不存在の両方が一致する |

ベンチマークでSQLiteを比較に使う場合は、同期設定、トランザクションの粒度、データ量を併記する。機能・保証の異なる結果を総合的な優劣へ結び付けない。SQLiteでも同期とcheckpointの頻度は速度・耐久性に関係する。[SQLite: Write-Ahead Logging](https://www.sqlite.org/wal.html)

## 7. 見積もりと範囲を削る順番

学習、実装、実験、文書化を含めた合計は**92〜144時間**を暫定見積もりとする。週8〜10時間なら約10〜18週という換算例になり、実際の週当たり時間は未確定である。GoやOSのI/Oが初めてなら別に20〜40時間程度の基礎学習を見込み、段階1の終了時に更新する。実際の速度保証ではない。

段階2までを42〜64時間の最初の判断点とし、永続化の仕組みに関心を持てるか、残る不確実性が何かを確認する。完成範囲を減らす場合は、計測条件の数、`inspect`の見栄え、配布先OSの追加から減らす。ログ検証、I/O失敗処理、復旧規則、排他制御は削らない。

段階5までを満たした時点でMVPは完成とする。数か月以上取り組む場合も、まずこの完成点を確保し、その後の拡張は次のうち1つだけを選ぶ。

- **容量管理:** 停止中の書き込みを前提に、新ログへ有効値を出力して同期し、同一ファイルシステム内のrenameと親ディレクトリ同期で切り替える。途中停止時に旧・新のどちらを使うか先に定義する。
- **複数操作の原子性:** バッチ全体のcommit記録と再生規則を加える。単なる複数PUTをトランザクションと呼ばない。
- **問い合わせ:** 小さな表と限定SQLを加える。SQL構文、型、エラーの仕様を別途定義する。
- **索引:** B+Treeなどの永続索引を追加し、索引更新とデータ更新の復旧を設計する。

容量管理またはバッチ原子性にさらに30〜60時間を見込むと、全体は122〜204時間、週8〜10時間の換算で約13〜26週となる。SQL・永続索引はこれとは別の追加見積もりを作り、完了済みMVPへ際限なく要件を足さない。

## 8. デモ・公開・費用

デモは「保存成功→プロセス停止→再起動→値が残る」「書き込み途中で停止→不完全な末尾を検出」「途中破損→理由付きで停止」の3本とする。障害点、応答履歴、復旧結果を同じ画面で示すと設計の説明につながる。

公開物にはソース、形式仕様、状態図、実験の再現コマンド、結果、限界を含める。実データや秘密情報は投入しない。生成ログは小さな公開fixtureだけを残し、通常のDBファイルや大量の計測生成物はGit対象外にする。

実行は手元のLinux環境で完結し、有料APIや常時稼働サーバーは不要。静的な説明ページを作る場合は[共通のホスティング方針](../AGENTS.md)に従いGitHub Pagesを使う。今回の作業では実装・公開・課金資源の作成を行っていない。

## 9. 確認した一次資料

以下は2026-10-14に確認した設計の参考資料である。上記の独自形式がSQLite互換であることや、SQLite相当の保存保証を持つことを意味しない。

- [SQLite: Atomic Commit](https://www.sqlite.org/atomiccommit.html): 保存装置への前提、同期、障害時の復旧を考える資料。
- [SQLite: Write-Ahead Logging](https://www.sqlite.org/wal.html): WAL、単一writer、checkpointと同期の関係を確認する資料。
- [Linux man-pages: fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html): ファイルとディレクトリの同期、失敗時の扱いを確認する資料。
- [Linux man-pages: rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html): 将来のログ切り替えで使う、名前の置換とファイルシステムの制約を確認する資料。
