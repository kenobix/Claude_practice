# 次の開発企画 — 目的に照らした再評価と詳細計画への案内

- 作成・再評価日: 2026-10-14
- 状態: 企画・作業計画。ここで提案する新規ソフトウェアは未実装。
- 目的: このリポジトリで未経験の仕組みを学び、動く成果・検証結果・設計判断を企業に説明できる作品を作る。
- ユーザーの回答: **ソフトウェア開発力を広く伸ばしたい。AI・機械学習エンジニアとしての能力も重視する。数か月以上かけて深く取り組める。** 週あたりの時間は未確定。

## 1. 再評価の結論

第一候補を**品質評価・配信・監視・切り戻しまで扱うMLOps基盤**に変更する。既存のモデル開発経験を土台に、データ契約、再現性、API、永続化、変更の審査、障害対応を横断して学べるため、今回明らかになった2つの目的に最も合うと判断した。

具体的には、公開データによる自転車レンタルの翌1時間の需要予測を題材に、1つのモデルを同じ条件で再学習でき、品質を比較し、どの版が配信され、悪化時にどこへ戻せるかを追えるシステムを作る。過去データの再生を使うため、実利用者の需要改善を達成したとは主張しない。成果は、入力・モデル・配信版の追跡と障害時の挙動を再現できる点に置く。

元の第一候補である**CIを題材にしたジョブ実行基盤**も有力である。非同期処理やバックエンドを最優先にするならこちらを選ぶ。残る5案も学習価値があるため削除せず、最小完成範囲を修正して個別計画を用意した。7本を順番にすべて実装する計画ではなく、主作品1本を選ぶための候補集とする。

## 2. 元の計画で修正した点

| 元の判断・不足 | 再評価と修正 |
|---|---|
| CI/CDを無条件の総合1位にした | 志望分野で適性が変わる。今回の回答を受けMLOpsを優先し、CIはバックエンド重視の選択肢に変更 |
| AI経験が多いためMLOpsの新規性を低く評価した | モデル学習と、版管理・配信・監視・回復の設計は別の経験。新しい学びを機能ごとに判断 |
| 5段階評価がほぼ高得点で差の根拠が弱い | 数値順位をやめ、既存との差・証明できる能力・完成上の難所を比較 |
| CI/CDという名称に対してデプロイの計画がない | CI用ジョブ実行基盤と呼び、CDは完成後の独立した発展課題へ |
| Webhookの重複排除から二重実行防止を広く述べた | 受付の冪等性と、Worker再試行による物理的な重複実行を区別。古い試行の結果を拒否する条件を追加 |
| コンテナの実行制限を終盤に置いた | 実際にコードを動かす段階から適用。コマンド名の許可だけで隔離を保証しない |
| DBや同期の機能範囲が大きい | DBは永続KVと復旧、同期は2クライアントとハブから始め、SQL・多拠点等は後に分ける |
| CI以外の作業計画がない | 7案それぞれに仕様、具体作業、完了条件、検証方法、概算工数、削る順、デモを追加 |
| 添付の所在を「このディレクトリ」と表現した | 元の参考案は会話に添付されたテキスト。リポジトリ内に存在するファイルとは扱わない |

テーマを新しい商用発明と見なす必要はない。既存製品が解いている問題を、自分で範囲を定めて実装・計測・説明できることが学習成果となる。企業への訴求は製品名や技術数から推測せず、レビューできる設計と再現できる実験で示す。

## 5. 推奨する進め方

1. **MLOps計画から始める。** まずデータの利用条件、予測時刻、使える特徴量、分割方法、比較するbaselineを決める。GPUや有料LLM APIを必要条件にしない。
2. **最初の完成を区切る。** 再現可能な学習、品質判定、モデルの版管理、API配信、手動昇格と切り戻しまでを一つの完成単位にする。
3. **今回の目的に向けた深掘りを行う。** 過去データ再生、入力変化の監視、遅れて届く正解による精度評価、再学習候補の生成を加える。新モデルを本番へ自動昇格させるところまで一度に広げない。
4. **成果をまとめてから次を選ぶ。** 永続化の原理が気になればDB、並行実行や復旧を掘り下げたければCI、利用者の同時操作なら共同編集へ進む。

MLOps内部のCIは既存のGitHub Actions等で構成し、自作Runnerの完成を前提にしない。DBエンジンの自作も、MLOpsの実データ保存に必要な前提にはしない。主題を1つに保つことで、数か月の時間を深い検証と改善に使う。

実装時間は各計画の範囲に応じた概算であり、採用する機能・環境構築・調査で変わる。ユーザーの週あたり時間は未確定なので、文書内の週数は換算例とする。最初の小さな動作ができた時点で残りを見積もり直し、数か月取り組めることを無制限の機能追加の理由にしない。

## 6. 全企画で共通に残す学習記録

| 節目 | 残す内容 | 自分で説明すること |
|---|---|---|
| 設計前 | 使う人、困りごと、完成範囲、前提 | 何ができれば最初の完成か |
| 中核実装前 | 入出力例、正常・異常時の予想、代替設計 | どの性質を守り、何を保証しないか |
| 最初の動作 | 再現コマンド、fixture、小さなテスト | ライブラリが担う部分と自作した部分 |
| 故障・境界の確認 | 注入条件、期待結果、実結果、修正前後 | なぜ壊れ、修正で何が変わったか |
| 計測 | 環境、データ/コード版、試行回数、生データ、集計 | 比較が公平か、別条件でも成り立つか |
| 作品化 | 構成図、3分デモ、起動手順、設計判断、既知の制約 | 他の実装案と比べなぜこれを選んだか |

各段階で、実装を読む前に自分の予想を書き、実行結果との差を説明する。重要な処理は小さな例を手で追ってから変更する。AIによるコード生成を使う場合も、状態遷移・評価方法・失敗理由の説明を自分で再構成することを完了条件に加える。

テストと障害実験は将来の実装計画に含めたもので、今回アプリを実装・計測して合格したことを意味しない。性能目標、合成データ、再生デモ、実測結果は成果物上でも区別する。

## 7. 公開と完成の判断

公開する資料はコード、再現手順、利用許諾に沿う小さなサンプル、匿名化した計測結果、設計の説明とする。静的な説明やデモは[共通ホスティング方針](../AGENTS.md)に沿ってGitHub Pagesを使う。Worker、WebSocket、永続DB等を含む実行環境は、まずローカルで完成させ、外部公開時に常駐処理・認証・費用に合うホストを別途選ぶ。

最初の作品は、正常動作に加えて主要な失敗を再現でき、クリーンな環境で起動でき、設計判断と限界を説明できたら完成とする。企業への訴求は、この証拠を相手の職種に合わせて見せることで具体化する。MLOpsならデータからモデル変更の判断まで、CIならジョブの整合性と復旧、DBなら保存とクラッシュ耐性を中心に説明する。

技術の前提は各計画にある一次資料で確認した。資料の仕様と、この企画で採用する簡略化・未対応事項を分けて記載している。将来実装に着手するときは、その時点の依存バージョンと対象環境に照らして再確認する。
