## 結論

第一候補として、**小規模な自作CI/CD実行基盤**を作る。GitHubのpushを受け取り、ジョブをキューに登録し、隔離したWorkerでビルドやテストを実行し、その状態・ログ・成果物をWeb画面から確認できるものを目指す。

これまでの成果にはWebアプリ、API連携、Docker、データ保存、AI・機械学習の幅広い実装がある。次は新しいモデルやチャット画面を増やすより、複数のプロセスが協調し、重複イベント・停止・再試行・復旧を扱うソフトウェアを作る方が、学びの幅を広げられる。CI基盤なら、個人開発でも使える道具になり、バックエンド・基盤・運用に関する設計判断を動く成果物と障害実験で示せる。

### 第一候補を選ぶ理由

- **既存資産を生かしながら新しい問題に進める。** React・API・SQLite・Dockerの既知要素を入口にしつつ、非同期ジョブの状態管理、再実行、重複排除、Worker障害、実行環境の隔離を新たに設計できる。
- **採用面談で具体的に説明できる。** 「作りました」だけでなく、イベントの重複やWorker停止をどう扱ったか、どの指標で改善を判断したかを、図・ログ・実験結果と合わせて示せる。
- **実用と学習をつなげられる。** 後続プロジェクトのビルドや静的チェックに使える。完成後はリポジトリへのpushから実行履歴確認までをデモできる。
- **範囲を小さく始められる。** 最初は自分が管理するサンプルリポジトリ、単一マシン、少数の固定コマンドに限定し、耐障害性や機能を段階追加できる。

添付案の「分散ファイル同期」は分散システムを深く学べるが、競合解決やデータ消失対策まで完成度を示すには実装範囲が大きい。「自作DB」はCSの基礎を掘り下げる最良の候補だが、企業向けの運用・サービス設計まで横断する点ではCI基盤に一歩譲る。まずCI基盤で実サービスの構築と運用を経験し、その次にDBエンジンまたは分散同期へ進む順がよいと考える。

## 第一候補の完成イメージ

```text
GitHub push
    ↓ HTTPS Webhook（署名・重複イベントを検証）
APIサーバー ── 実行履歴・キュー ── 永続DB
    ↓
Worker ── 使い捨て実行環境でビルド・チェック
    ↓
状態・ログ・成果物 ── Webダッシュボード
```

最初の利用先は自分の管理下にあるサンプルリポジトリとする。GitHub Pagesはフロントエンドのデモに使えても、ジョブを実行するサーバーの代わりにはならない。実行基盤はまずローカルのDocker Composeで起動する構成にし、公開デモが必要になった段階でホスト先を検討する。

## 段階的な開発計画

### Phase 0: 問題設定と設計

- 対象を「自分が管理する1つのリポジトリのpush」に絞る。
- 代表的な成功・失敗・重複Webhook・タイムアウト・Worker停止のシナリオを定義する。
- コンポーネント図、状態遷移図、脅威モデル、API案、データモデルを作る。
- 各設計判断について、採用案・代替案・理由を短く記録する。

**完了条件:** どのイベントがどの状態変化を起こし、障害後に何が起きるかを図と文章で説明できる。

### Phase 1: キューとWorkerの最小縦切り

- Web APIから手動でジョブを登録できるようにする。
- DBにジョブ状態（queued / running / succeeded / failed）と作成・開始・終了時刻を保存する。
- Workerがジョブを取得し、許可済みの短いコマンドを実行する。
- 標準出力・標準エラー、終了コード、実行時間を履歴に保存して画面に表示する。

**完了条件:** 1件のジョブが登録から結果閲覧まで通り、サーバー再起動後にも履歴が残る。

### Phase 2: ワークフローとWebhook

- リポジトリごとに宣言した固定ステップ（例: install、lint、test、build）を順番に実行する。
- GitHub Webhookの署名を検証し、pushイベントからジョブを作る。
- delivery IDなどで同じイベントが複数回来ても同じジョブが重複作成されないようにする。
- ブランチ・パスなどの対象条件を小さく実装する。

**完了条件:** サンプルリポジトリへのpushが1回の実行履歴になり、Webhook再送によって二重実行されない。

### Phase 3: 障害復旧と運用性

- Workerのリースまたはハートビートを導入し、実行中にWorkerが消えたジョブを検出する。
- 再試行回数、待機時間、タイムアウト、手動キャンセルの動作を定義する。
- 同時実行数に上限を設け、キュー待ち時間・実行時間・成功率を記録する。
- Worker強制停止、DB再起動、同一Webhook再送などの障害実験を行い、結果を記録する。

**完了条件:** 障害シナリオごとに検出方法・復旧動作・データの最終状態を説明できる。

### Phase 4: 実行境界とポートフォリオ仕上げ

- コマンド許可リスト、コンテナのCPU・メモリ・実行時間制限、読み取り専用領域などを適用する。
- MVPでは自分が管理する信頼済みコードだけを対象にする。外部利用者の任意コードを実行する公開サービスにはしない。
- デモ動画または画面キャプチャ、アーキテクチャ図、障害実験表、計測結果、既知の制約をREADMEに整理する。
- クリーンな環境から起動できる手順と、成功・失敗両方のデモ手順を用意する。

**完了条件:** 第三者が構成とトレードオフを読み取り、ローカルでデモできる。実験結果で信頼性に関する判断を裏付けられる。

## 学習効果と成果の測り方

完成した機能数ではなく、システムの性質と根拠を示す。

- **正しさ:** 同じWebhookの再送数に対し、作成されるジョブ件数が意図どおりであること。
- **復旧:** Worker停止後にジョブが孤立しないか、回復までの時間と最終状態。
- **性能:** 連続投入したジョブの処理件数、キュー待ち時間、実行時間の中央値とp95。
- **制御:** タイムアウト・同時実行上限・リソース制限が設定どおり働くこと。
- **説明力:** 状態遷移、障害時の挙動、セキュリティ境界、採用しなかった代替案を自分の言葉で説明できること。

計測値は実験条件・サンプル数とともに記録する。ポートフォリオでは、根拠のない「高可用」「本番対応」といった表現を避け、確認した範囲と未対応の範囲を明記する。

## 実装時の設計方針

- 技術選定を先に固定せず、まず状態遷移・信頼境界・復旧要件を定義してから必要最小限の構成を選ぶ。
- 重要な仕組み（ジョブ状態遷移、重複排除、Workerの回復判定）はライブラリ任せにせず、実装と動作を自分で説明できる形にする。
- ただし、暗号やコンテナ隔離を独自に発明しない。署名検証やコンテナ実行は標準的な仕組みを利用し、その境界と限界を学ぶ。
- 任意コード実行の危険を前提にする。最初は信頼済みの自分のリポジトリだけを許可し、公開Runner・秘密情報の注入・外部Pull Requestの実行はMVPに含めない。
- 小さく動く縦切りを節目にして、設計・実験・運用の記録を同じ日付ディレクトリに残す。

## 次点の進め方

CI基盤が期待する学びにならなかった場合は、候補の中から次を選ぶ。

1. **自作データベースエンジン:** Webサービスの運用より、データ構造・永続化・ACID・障害復旧を深く理解したい場合。
2. **PCAP解析ツール:** ネットワークとセキュリティの実践を優先し、保存済みパケットの解析から始めたい場合。
3. **分散ファイル同期:** 競合・オフライン・再同期を中心に、分散システムを長期テーマとして掘り下げたい場合。

## 最終提案

まずPhase 0〜1を完成させ、ジョブキュー・Worker・実行履歴の縦切りを動かす。その時点で学習価値と作業量を見直してから、Webhook、障害復旧、隔離、ポートフォリオ化へ進む。最初から大規模なGitHub Actions互換を目指さず、小さくても自分で障害を再現し、理由を説明できる実行基盤を完成させる。
