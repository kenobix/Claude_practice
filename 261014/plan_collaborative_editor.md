# リアルタイム共同編集アプリの詳細計画

- 作成・資料確認日: 2026-10-14
- 状態: **企画・未実装**。以下の完了条件と測定値は、今後実装して確認するもの。
- 位置づけ: ブラウザ、ネットワーク、永続化をまたぐ整合性を深く学ぶ選択肢。
- 総合比較: [次に作るソフトウェアの計画](next_project_plan.md)

## 1. 目的と企画の妥当性

2〜3人で同じテキストを編集し、一時的な切断中も書き続け、再接続後に編集内容が収束するアプリを作る。利用場面は、小規模な勉強会の議事メモや共同学習ノートとする。

新しい学習の中心は、同時編集、更新順序の逆転、重複配送、端末ごとの未送信変更、権限変更とオフライン編集の関係である。画面上で2人の変更が合流する様子と、停止後の復旧を続けて見せられるため、成果の説明に向く。

Yjsとエディターを接続するだけで完成にすると、ライブラリの利用例で止まりやすい。更新配送の実験、サーバー側の保存確認、文書削除と権限失効を実装・記録することを、この企画の完成条件に含める。

| 既存成果 | 再利用できる経験 | 今回増やす経験 |
|---|---|---|
| [260905のフラッシュカード](../260905/README.md) | ブラウザ保存、編集画面、元に戻す操作 | 複数端末間の編集合流、通信の切断、保存先ごとの状態表示 |
| [260406のダッシュボード](../260406/dashboard/README.md) | React、API、SQLite、Docker | WebSocketの接続管理、更新ログ、アクセス権限と同期の境界 |
| [260702の分散概念学習](../260702/work_log.md) | 複数ノードの状態を考える視点 | 実際のブラウザとサーバー間での再接続・永続化 |

上記の記録では共同編集サービスの実装を確認していない。全ファイルを実行して未実装を証明したという意味ではない。

## 2. 利用者と最小完成範囲

利用者は、事前に登録した3つのデモ用アカウントとする。文書所有者が編集者・閲覧者を指定する。公開の新規登録や匿名の編集参加は、初期版に含めない。

**最小完成版に含めるもの**

1. プレーンテキスト文書の作成、一覧、編集、論理削除。
2. 1文書につき3クライアントを基準とする同時編集と接続状態表示。
3. IndexedDBへの端末内保存、未送信変更の再送、サーバーへの保存確認。
4. 単一同期サーバーと永続DBからの文書復元。
5. 所有者・編集者・閲覧者の区別と、失効後の更新拒否。
6. 重複配送・切断・再起動・権限変更を再現できるデモ。

後回しにするものは、リッチテキスト、画像、コメント、変更履歴UI、複数サーバー、音声通話、公開招待、スマートフォン最適化である。Markdownのプレビューも追加機能とし、初期版はテキストに絞る。

## 3. 暫定構成と責任の分担

```text
ブラウザA/B/C
  エディター + Y.Doc/Y.Text + IndexedDB + 送信待ち更新
        │ WebSocket: 同期・更新・保存確認・接続中ユーザー
        ▼
Node.js同期サーバー + セッション認証 + 文書ごとの権限確認
        │ 文書単位で更新・権限変更を順序づける
        ▼
SQLite: 文書属性・権限・更新ログ・スナップショット
```

- UIはTypeScript、React、CodeMirror系のエディターを暫定候補とする。採用するYjs連携の対応版は実装開始時に固定する。
- 文書の収束にはYjsを使う。CRDTそのものを本番用に独自実装することは必須にしない。
- 接続処理は[y-websocket](https://docs.yjs.dev/ecosystem/connection-provider/y-websocket)を参考にし、`y-protocols`を利用して保存確認・権限確認を追加する。利用版のプロトコルを設計メモに残す。
- 接続中ユーザーやカーソルはAwareness、文書内容はYjs document updatesで扱う。Awarenessを文書の永続更新ログに保存しない。[Yjs Awareness](https://docs.yjs.dev/api/about-awareness)
- オフライン保存には`y-indexeddb`を候補とする。ページ自体をオフラインで初めて開けることは別機能であり、MVPは一度ロード済みのページからの切断を対象とする。[Yjs Offline Support](https://docs.yjs.dev/getting-started/allowing-offline-editing)
- SQLiteは単一サーバーが書き込む。保存先はDockerの永続ボリュームとし、DB設定・バックアップ手順も記録する。

## 4. データ契約と不変条件

| データ | 必須項目・扱い |
|---|---|
| 文書 | 再利用しない`document_id`、所有者、`active/deleted`、権限版、作成日時 |
| 権限 | `document_id`、`user_id`、`owner/editor/viewer`、変更日時 |
| 永続更新 | 文書ID、送信者、端末ID、`message_id`、更新ハッシュ、受理順番号、バイナリ更新、受理日時 |
| スナップショット | 文書ID、包含済みの受理順番号、Yjs状態、作成日時 |
| 端末内データ | ユーザーID・文書IDごとのYjs状態、未確認の送信更新 |
| 一時状態 | 接続・カーソル・表示名。認可の根拠にはしない |

Yjsの更新は順序変更・重複適用に対応し、必要な更新が全参加者へ届けば状態が収束する。通信断中の即時一致や保存の耐久性は、別途実装する。[Yjs Document Updates](https://docs.yjs.dev/api/document-updates)

次を必ず守る。

1. サーバーは認証済み接続からのみ更新を受け付け、文書IDだけで閲覧・編集を許可しない。
2. 接続時だけでなく更新受理時も権限と削除状態を確認する。同期メッセージ内の更新も同じ検査対象にする。
3. 文書ごとに更新受理と権限変更を直列化し、権限失効が確定した後の更新をDBへ書かない。
4. 更新を文書の一時コピーへ適用して形式・上限を検査し、DBへコミットした後に正式なメモリ状態へ反映・配信・保存確認を行う。拒否した更新を他端末に流さない。commit後に停止した場合はログから復元する。接続完了やYjsの同期完了を「サーバー保存済み」と表示しない。
5. 保存確認が失われた場合は同じ更新を再送する。`document_id + user_id + client_id + message_id`で再受理を識別し、同じIDで異なる更新ハッシュなら拒否する。保存確認はその更新だけに対応させ、後続の未確認編集があれば「サーバー保存待ち」を維持する。
6. スナップショットに未包含の更新を削除しない。圧縮は文書単位で止めた処理、または包含境界を固定したトランザクションで行う。
7. 文書の論理削除後は旧IDへの同期を拒否する。空の文書を同じIDで自動生成しない。
8. 削除・権限失効を受けた端末の未送信内容は、同期停止と理由を表示し、ローカルに書き出せる。自動で別文書へ公開しない。
9. 既に端末に取得された文書を遠隔から完全消去できるとは約束しない。ログアウト時のキャッシュ破棄と、再接続時の認可を扱う。
10. 本文をHTMLとして直接挿入しない。文書・更新サイズと送信頻度に上限を設け、超過時のエラーを定義する。

初期の上限案は可視本文10万UTF-16コード単位、更新メッセージと文書の完全なYjs状態はそれぞれ8MiB、同時3クライアントとする。差分更新だけでなく再接続時の全状態も同じ上限で送れるかを検証する。上限を超えた文書は同期を止め、ローカル内容を書き出せるようにする。これは性能実績ではなく試験範囲であり、Phase 0の文字コード・バイナリサイズ確認後に確定する。

## 5. 段階別の作業計画

### Phase 0: 収束の仕組みと境界を理解する（12〜20時間）

- 学習用に小さなG-Counterを作り、加算・マージ・重複配送を説明する。これは共同テキスト編集の実装とは別の練習とする。
- 3個のY.Docに同時挿入・削除を行い、更新の逆順配送・重複・一時保留・後送を試す。
- テキスト結果と各端末の更新受領を比較し、収束条件と「通信できなければ収束しない」限界を記述する。
- 保存場所ごとの状態と、権限失効・文書削除の状態遷移を図にする。
- 成果物: `docs/design.md`、更新配送実験、`docs/decisions/`。
- 完了条件: CRDTの収束、配送、永続化、認可を分けて自分の言葉で説明できる。

### Phase 1: オンライン共同編集（18〜28時間）

- 3つのデモアカウント、セッション、文書作成・一覧と権限表を用意する。
- エディターとY.Textを接続し、WebSocket経由で同時変更を届ける。
- 全文置換による送信ループを避け、エディターの差分・Yjs transaction originの扱いを確認する。
- 接続中ユーザーと接続状態を表示し、閲覧者による更新メッセージをサーバーで拒否する。
- 成果物: 2ブラウザで動く縦切り、通信シーケンス、起動手順。
- 完了条件: 同時入力が最終的に一致し、他人の文書への接続・変更が拒否される。

### Phase 2: 永続化と切断復帰（24〜38時間）

- 更新ログ、スナップショット、文書ロードを実装する。ロード完了前に空文書で同期を開始しない。
- 端末内保存と送信待ち一覧、サーバーの保存確認を実装する。
- IndexedDB内のYjs状態と送信待ち一覧が片方だけ保存された場合を試す。一覧だけを再送の根拠にせず、保存済みY.Docとサーバーのstate vectorから不足更新を再生成し、通常の認可・永続化・保存確認の経路で送る。
- 「端末内保存済み」「サーバー保存待ち」「サーバー保存済み」の表示を分ける。
- 端末内の保留更新から再送し、state vectorによる不足更新の同期と整合させる。
- DBコミット前後・保存確認送信前後の停止を実験する。
- 成果物: 更新スキーマ、再送フロー、復旧記録。
- 完了条件: サーバーが保存確認済みの変更が再起動後に残り、確認前の変更も端末から再送できる。

### Phase 3: 権限失効・削除・不正な更新（18〜30時間）

- 所有者が権限を変更したら接続を閉じ、以後の同期・更新受理に新しい権限を使う。
- 切断中の編集者を閲覧者へ変更し、再接続時のアップロード拒否とローカル書き出しを実装する。
- 文書削除後の旧端末参加を拒否し、文書が復活しないことを確認する。
- サイズ超過、破損した更新、未知の文書、期限切れセッションを扱う。
- 成果物: 権限試験表、エラー一覧、ユーザー向け復旧手順。
- 完了条件: 正常系と同じ経路で拒否条件が働き、拒否された更新が他端末に流れない。

### Phase 4: 再現可能なデモと運用資料（18〜28時間）

- 下表の障害実験を固定seed・手順・バージョンとともに記録する。
- 日本語IME、絵文字、改行、貼り付け、元に戻す操作を確認する。
- 100件程度の更新で配送時間、再同期時間、送信量、DB増加量を記録する。測定件数と機器を併記する。
- バックアップからの復元を試し、文書と権限を同じ時点で復元する手順を残す。
- 成果物: `docs/experiments.md`、デモ動画、構成図、README、既知の制約。
- 完了条件: 第三者が2ブラウザの共同編集・切断復帰・権限失効のデモを再現できる。

**ここで最小完成版として公開資料をまとめる。** 続ける場合は、各20〜40時間を目安に更新ログの圧縮、編集履歴と個人Undo、リッチテキストのいずれか1つを選ぶ。複数サーバー対応は別企画として再設計する。

## 6. 検証と障害実験

| 条件 | 確認する結果 |
|---|---|
| 同じ位置へ同時挿入・同時削除 | 全更新配送後に本文が一致する。文章の意味が自然になる保証とは区別する |
| 更新の逆順・重複・一部保留 | 保留分の配送後に収束し、重複分で文字が増えない |
| 片側を切断して双方編集 | 再接続で合流し、保留状態から保存済みへ遷移する |
| サーバー保存直後に確認応答を喪失 | 再送が成功し、永続更新の重複扱いが説明できる |
| サーバー・ブラウザを別々に再起動 | 各保存先の残存範囲が仕様どおりで、空文書で上書きされない |
| 切断中に編集権限を失効 | 再参加時に変更を受理せず、端末側で復旧方法を示す |
| 文書削除後に旧端末が再参加 | 自動復活せず、別ユーザーへのキャッシュ混入もない |
| 大きな更新・壊れたバイナリ | 当該更新を拒否し、既存文書を壊さない |

別ブラウザプロファイルで試験し、同一ブラウザ内のBroadcastChannelによる通信を切断試験と取り違えない。Yjs状態のバイナリ一致だけで判定せず、可視テキストと追加同期後の状態を確認する。

## 7. 工数・縮小方法・続行判断

MVPの合計は**90〜144時間**。学習、実装、検証、資料化を含む個人制作の概算である。週の作業時間は未確定であり、週8〜10時間なら約9〜18週という換算例になる。Phase 0終了後に再見積もりする。

削る順は、カーソルの装飾、編集履歴UI、Markdownプレビュー、複数文書の利便機能、3人から2人への試験範囲縮小とする。保存確認、再送、権限失効、削除後の再参加拒否は残す。

Phase 2で「保存された更新と未保存の更新」を説明できなければ、機能追加を止めて保存境界を修正する。Phase 4を満たせば完了とし、機能数を増やす目的で延長しない。

## 8. デモ、企業へ示す証拠、公開と費用

3分のデモは「2人で編集→片側切断→双方編集→復帰して合流→片側の権限失効→更新拒否」の順にする。別の短い動画でサーバー再起動後の復元を示す。

説明資料には、更新配送の実験ログ、保存確認の境界、拒否ケース、復旧時間の実測、採用しなかった案を残す。「リアルタイムアプリを作った」から一歩進み、失われる可能性がある変更と、失われないと確認した変更を説明できる状態を目指す。

開発・デモはローカルのDocker Composeを基本とする。追加クラウド契約や有料APIはMVPの前提にしない。常時公開する場合はWebSocket接続と永続ディスクを維持できる実行環境を選び、停止・バックアップ・月額上限を別途決める。

GitHub Pagesには紹介・実験結果・録画を掲載できる。共同編集サーバー本体は動かせないため、公開判断は[ホスティング方針](../260805/hosting_policy.md)に従って用途別に記録する。MVP段階で常時公開する必要はない。
