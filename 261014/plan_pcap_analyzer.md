- 作成・見直し日: 2026-10-14
- 状態: **未実装の開発計画**。以下の数値は目標・見積もりであり、実測結果ではない。
- 位置づけ: ネットワークの基礎と、観測データの限界を扱う開発力を深める独立候補。
- 総合判断・他候補: [次のプロジェクトの選び方](next_project_plan.md)

## 目的と見直し判断

自作の小さな通信記録を読み、通信量、通信相手、DNSの応答、解析できなかった範囲を説明するローカルCLIを作る。
利用者は、ネットワークを学ぶ自分と、保存済みの実験記録から接続不調の手掛かりを調べたい開発者を想定する。
「通信が遅い」「DNS応答が見つからない」といった問いに、根拠のパケット番号を示して答える道具を目指す。

元案の方向性は妥当だが、「異常検知」を初期目標にすると、正解ラベルや捕捉範囲が不明なまま攻撃判定に進みやすい。
最初は集計と観測条件の説明に絞り、再送らしき挙動や未応答は**調査の手掛かり**として扱う。
自作部分はフロー集計、DNS照合、根拠追跡、欠測の扱いとし、パケットの全プロトコル実装は目指さない。

## 最小完成範囲

1. 保存済みの非圧縮classic pcapを受け取り、Ethernet上のIPv4・TCP/UDPのヘッダーを読む。
2. パケット数、捕捉バイト数、記録上の元フレーム長、時刻範囲、方向別通信量をJSONと端末表に出す。
3. フラグメント化されていないUDP DNSの問い合わせと応答を照合し、応答までの観測時間を出す。
4. 不完全・未対応・壊れた入力を区別し、解析できた割合と根拠パケット番号を残す。
5. 生成条件が明確なfixture、期待値、TSharkとの比較結果、3分のデモを添える。

pcapng、IPv6、VLAN、Linux cooked capture、Wi-Fi、ライブ捕捉、TCP再構成、TLS復号は後回しにする。
MVPは対応外の形式を自動変換せず、理由と対処を返す。Ethernetかどうかは拡張子ではなくlink typeで確認する。
任意のPCAPをアップロードするWebサービス、攻撃の自動断定、通信先の評判照会、機械学習による分類は含めない。
数か月取り組む場合も、まずこの範囲を完成させ、次に一つの拡張を選ぶ。

## 暫定技術と構成

PythonとScapyを候補とし、CLIは標準ライブラリの`argparse`、出力はJSONとする。
Scapyの`RawPcapReader`が持つ時刻・`caplen`・`wirelen`を入力境界で取り出し、Ethernet/IPの復号にライブラリを使う。
一括で全パケットを保持せず、順次読み込み、集計結果と必要な参照番号を残す。[Scapy公式API](https://scapy.readthedocs.io/en/latest/api/scapy.utils.html#scapy.utils.RawPcapReader)

```text
保存済みpcap → 入力検証 → ヘッダー抽出 → PacketRecord
                                         ├→ フロー集計
                                         ├→ DNS照合
                                         └→ 解析品質の集計
                                              ↓
                                        JSON / 端末表
```

将来の配置案は`<開始日>/pcap_analyzer/`とし、`reader.py`、`flows.py`、`dns.py`、`report.py`を責務で分ける。
`fixtures/`に小さな自作記録と生成スクリプト、`expected/`に手計算した期待値、`docs/`に仕様と測定条件を置く。
依存関係は実装開始時に対応するPythonと組み合わせを確認して固定し、ライブラリの例外をCLIの診断へ変換する。

## データ仕様と守る条件

| 項目 | 初期仕様 |
|---|---|
| `PacketRecord` | `packet_index`、`timestamp_ns`、`captured_len`、`original_len`、IP・ポート・プロトコル、解析状態 |
| 時刻 | pcapの精度を確認し整数nsへ正規化。元がµsなら、ns精度で観測したとは表現しない |
| フローキー | プロトコルと、IPのバイト列・ポートで順序を固定した両端点。方向は別フィールド |
| フローの意味 | 同じ両端点の通信の集計。MVPではポート再利用を含み得るため、単一TCP接続とは呼ばない |
| DNSキー | client/serverのIP・ポート、ID、正規化した問い合わせ名、type、class |
| 解析状態 | `parsed` / `unsupported` / `truncated` / `malformed`のいずれか一つ。詳細理由を併記 |
| レポート | `schema_version`、入力SHA-256、ツール・設定の版、件数、未対応範囲、根拠参照 |

DNSは最初の対象を質問が1件のメッセージに限定し、複数質問は未対応として数える。
問い合わせ名のキーは展開後のラベル列で保持し、ASCIIのA〜Zだけを小文字化する。終端ルートは1つとして扱い、非ASCIIバイトをUnicode変換で同一視しない。表示用の名前はエスケープし、表示文字列のドット分割からキーを作り直さない。
初期版は送信元または宛先ポート53のUDPを候補とし、DNSヘッダー・長さを検査してから解析する。
応答の有無と名前解決の成功は分け、RCODEとTCフラグを保存する。NXDOMAINも応答時間のある否定応答である。
照合窓は暫定5秒とし、その窓で同じキーの未確定問い合わせが複数あれば`ambiguous`にする。最後の問い合わせからの時間を黙って採用しない。
完了後も窓の終わりまでキーの履歴を保持し、その間の同じキーの再利用は遅延・重複応答と区別できないため、応答時間の集計から除外する。窓の後の再利用は別の問い合わせとして扱う。この窓に基づく規則による照合であり、実通信の対応関係を完全に証明するものではない。
完了キーへの追加応答は`additional_response`、未確定問い合わせのない応答は`unmatched_response`とし、窓外の応答で過去の未応答判定を成功へ変更しない。質問0件の応答はMVPでは未対応とする。
応答時間は上記の規則で一意に対応したペアだけの`response_time_ms`である。
記録の終了で待機時間を観測できない問い合わせは`window_incomplete`、窓内に応答がないものは`no_response_observed`とする。
これらは観測状態であり、DNSサーバーの障害やパケット損失の確定ではない。
パケット分類の合計は読めたレコード数と一致させ、DNSの状態集計はその内訳とは別の指標として保持する。
分類が重なる場合は、長さ矛盾等の`malformed`、捕捉不足の`truncated`、対象外プロトコル等の`unsupported`、`parsed`の順に優先する。MVPではtruncatedのパケットをDNS照合から除外し、確認できる捕捉バイト数だけを集計する。
再送・重複パケットも実際に捕捉した通信量として数え、アプリケーションが届けた一意なバイト数とは区別する。
`captured_len`と`original_len`を分け、捕捉長を通信回線の実転送量と呼ばない。
入力は読み取り専用、DNS逆引きや外部API呼び出しは行わず、同じ入力と設定から同じ集計を得る。

## 観測限界をどう表すか

- 記録が途中から始まる、片方向しか見えない、キャプチャ側が取りこぼす場合がある。見えない通信を「存在しない」と結論しない。
- pcapの切り詰めとIPv4のフラグメントを区別する。初期版はフラグメントをIP段階で計数し、TCP/UDP/DNS解析から除く。
- TCPの順序逆転、再送、重複捕捉は区別が難しい。再送推定を追加する場合は、根拠と曖昧さを表示する。[Wireshark TCP Analysis](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvTCPAnalysis.html)
- TLSで暗号化されたアプリケーション本文は、このツールの入力だけでは読めない。ポート443だけでTLSと断定もしない。[Wireshark TLS](https://wiki.wireshark.org/TLS)
- 元記録にないHTTP本文、認証情報、DNS over HTTPSの問い合わせ内容は復元しない。初期版のDNSは平文UDP DNSのみである。
- 時刻が逆行する記録では、そのファイル全体の時間依存のDNS集計を無効にし、件数と警告を出す。都合のよい並べ替えで問題を隠さない。

## 段階別の作業計画

### Phase 0: 入力条件と期待値を先に決める — 8〜12時間

対応形式・最大入力サイズ・正常/異常の扱いを`docs/spec.md`に記載する。
固定した時刻・アドレス・DNS名で、TCP通信、DNS成功、未応答、重複問い合わせの小さなfixtureを設計する。
fixtureは送信せずファイルとして合成し、生成レシピと期待するパケット数・バイト数を記録する。
**成果物:** 仕様、fixture設計表、期待値、コンポーネント図。
**完了条件:** 各指標の計算式と、解析できない場合の表示を入力例から説明できる。

### Phase 1: 読み込みと件数集計 — 12〜18時間

入力形式、link type、長さを検査し、パケット番号を保持した`PacketRecord`へ変換する。
壊れたグローバルヘッダーは処理失敗にし、壊れた個別レコードでは正常終了に見せず不完全と報告する。
宣言されたcaplenと実際に読めた長さ、末尾の不完全なレコードを確認し、ライブラリがEOF扱いする場合も検出する。
暫定上限は入力100MiB、100万レコードとし、いずれかの上限で明示的に停止する。
**成果物:** CLI、読み込み層、集計JSON、上限・診断コードの仕様。
**完了条件:** 正常・空・未対応・破損の各入力が規定どおり終わり、読み取れた件数が一致する。

### Phase 2: フローとDNS照合 — 16〜24時間

双方向のフロー集計、片方向の件数、TCPフラグ別件数、DNSの状態別集計を実装する。
未完了DNSキー数とフロー数にも上限を定め、メモリに無制限に残さない。
窓が閉じたDNS項目を確定し、レポートに根拠パケット番号と、時間を計算できた条件を表示する。
**成果物:** フロー一覧、DNS照合表、手計算と一致する小さな実例。
**完了条件:** 重複ID・順序逆転・記録終端・フラグメントを、成功応答と混同しない。

### Phase 3: 独立した基準との比較 — 12〜18時間

同じfixtureをTSharkで読み、フレーム数、捕捉長、IP、ポート等の共通定義を比較する。
TSharkの版・フィルター・設定・コマンドを記録し、独自のDNS状態区分まで一致するとは仮定しない。
TSharkは保存ファイルの読み込みとフィールド抽出を比較の入口に使える。[TShark公式マニュアル](https://www.wireshark.org/docs/man-pages/tshark.html)
**成果物:** 比較スクリプト、差分の理由、異常系の結果表。
**完了条件:** 対応範囲の相違が説明でき、未説明の差が残らない。

### Phase 4: 再現手順とデモ — 8〜12時間

インストール、fixture生成、CLI解析、結果照合をREADMEから再現できるようにする。
固定した入力規模ごとの処理時間・最大メモリ・解析状態の割合を記録する。
**成果物:** README、3分動画、設計判断、既知の制約、計測記録。
**完了条件:** 他者が実通信を捕捉しなくても、成功例と解析限界の両方を再現できる。ここをMVP完成とする。

### 深掘り: 完成後に一つ選ぶ — 追加24〜50時間

候補は、pcapng/IPv6対応、TCP接続区切りと再送推定、静的HTMLレポートのいずれかとする。
TCP推定なら、シーケンス番号の周回、SYN/FIN、重なり、順序逆転、片方向捕捉を仕様化してから着手する。
AI/MLへ広げる場合は、特徴量の意味、ラベルの作り方、時間分割、誤検出を評価できるデータ計画を別に作る。
「異常な通信がある」ことと「攻撃である」ことを同じ教師ラベルにしない。

## 検証計画と異常系

| 入力・操作 | 期待する挙動 |
|---|---|
| 既知の小さなTCP/UDP記録 | 手計算とパケット数・長さ・方向が一致 |
| 空ファイル / pcapヘッダーだけ | 前者は形式エラー、後者は0件の有効記録 |
| caplen未満で終わるファイル | 不完全な入力と診断し、成功レポート扱いにしない |
| 元長より捕捉長が短いパケット | `truncated`として集計し、不足部分を推測で補わない |
| IPフラグメント・未対応link type | 対応範囲外を明示し、誤ったポートやDNSを出さない |
| 同じDNS ID、別名/別ポート | キーが異なる問い合わせを混同しない |
| 重複問い合わせ、応答だけ、時刻逆行 | 曖昧・対応なし・時間解析停止を区別 |
| 入力・件数・フロー数の上限超過 | 理由を表示して停止し、途中結果に不完全と明記 |

入力を1件追加したとき件数と長さが規定分だけ増える性質や、同じ記録の再実行の一致も確認する。
Scapyで生成したものをScapyで読むだけでは共通の誤りを見逃すため、手計算とTSharkの双方を参照する。
性能は同じマシン・入力・版で複数回測定し、結果を得る前から高速性を保証しない。

## 工数と範囲を削る順序

MVPは学習・実装・不具合修正・資料化を含め**56〜84時間**、深掘りは別に**24〜50時間**を見込む。
週8〜10時間ならMVPは約6〜11週という換算例であり、毎週の可処分時間は未確定である。
最初のPhase 1の実績で見積もりを更新し、未経験の形式処理に時間がかかれば期間を延ばす。
短縮時は、HTML表示、追加形式、TCP推定の順に見送り、DNS照合を別マイルストーンに分ける。
DNSを延期した版は「通信量集計の中間版」と明記し、この計画全体のMVP完成とは区別する。
入力検証、件数の整合、未対応・欠測の表示、根拠番号、再現用fixtureは完成条件として維持する。

## 3分デモと企業へ説明する証拠

0〜40秒で正常な記録を読み、通信量とDNS応答の一覧から根拠パケットへたどる。
40〜100秒で未応答・重複・切り詰めの記録を読み、断定できることと観測不足を画面で示す。
100〜150秒で同じ記録のTShark比較と不一致の解消記録を示す。
150〜180秒で対応範囲と次に増やす機能、その設計理由を説明する。
提出する証拠は仕様、実装、fixture、期待値、比較結果、性能条件、設計判断の記録である。
ネットワーク・バックエンド・運用に関する説明材料になるが、採用評価や業務利用可能性を保証するものではない。
