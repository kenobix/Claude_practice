# Codex移行・リポジトリ運用計画

- **作成日:** 2026-10-14
- **文書の用途:** 確定した移行方針と実施手順
- **対象:** `kenobix/Claude_practice` とローカル作業ディレクトリ `/home/kenshin/work/claude_practice`

この文書は、Claude Code中心で運用してきた既存リポジトリを、今後Codexでも継続して使うための実施計画です。リポジトリ名の変更、新規リポジトリへの移動、GitHub PagesのURL変更は今回の計画に含めません。

## 1. 決定事項

| 項目 | 方針 |
|---|---|
| GitHubリポジトリ | `kenobix/Claude_practice`を維持する |
| ローカルディレクトリ | `claude_practice`を維持する |
| Git履歴・既存成果物 | 現在のリポジトリに継続して蓄積する |
| Codexの指示ファイル | ルートの`AGENTS.md`を共通指示の正本にする |
| Claude Codeとの互換性 | ルートの`CLAUDE.md`から`AGENTS.md`を読み込む |
| 公開上の表記 | READMEとPagesトップの説明をツール非依存の表現に整える |
| 公開URL | `https://kenobix.github.io/Claude_practice/`を維持する |
| commit・push | 差分レビュー後、ユーザーの指示とリポジトリのGit運用方針に従う |

Codexを使うこと自体は、リポジトリ名を変更したりリポジトリを分けたりする理由にはなりません。今後の成果物にはClaude Code以外の生成AI、機械学習、ソフトウェア開発の内容も含まれるため、公開ページの説明は広いテーマに合わせます。

## 3. リポジトリ名と分離方針

### 3.1 現在の名前を維持する理由

このリポジトリには学習記録、アプリ、ポートフォリオなどが蓄積され、GitHub Pagesの公開URLもリポジトリ名を含みます。GitHubでリポジトリ名を変更すると、通常のリポジトリURLやGit操作は旧名から転送されますが、GitHub PagesのプロジェクトサイトURLは自動転送の例外です。現在の公開URLやREADME内のリンク、外部で共有されたリンクに影響するため、Codexへの切り替えだけを理由に変更しません。

リポジトリ名と、そこで使うコーディングツール名は別々に決められます。ローカルディレクトリ名もGitHub上の名前とは独立しており、変更は不要です。

### 3.2 新規リポジトリを作る判断基準

学習記録全体を複製して新しいCodex用リポジトリを作ることは、現時点では行いません。新しいリポジトリを検討するのは、成果物が独立したプロジェクトとして次のような運用を必要とするときです。

- 独自のリリース、バージョン管理、変更履歴が必要。
- 独立したCI/CD、デプロイ設定、依存関係管理が必要。
- 専用のIssue、Pull Request、コラボレーター管理が必要。
- 学習ログとは異なるREADME、ライセンス、サポート方針を持たせたい。

その場合は、対象プロジェクトを分離する計画を別途作成します。Git履歴を引き継ぐか、GitHub Pagesの新しいベースURLをどう扱うか、既存ログから新リポジトリへのリンクをどう設けるかを先に決めます。

### 3.3 「クローン」と「新規リポジトリ」の区別

`git clone`はリモートリポジトリのローカル作業コピーを作ります。通常、クローン先の`origin`は元のGitHubリポジトリを指すため、GitHub上に独立したリポジトリは作られません。別のGitHubリポジトリとして運用する場合は、新規作成・Import・Forkなどを選び、履歴、Issue、Pages、設定の扱いを個別に決めます。

## 4. エージェント向け指示ファイルの構成

### 4.1 `AGENTS.md`を共通指示の正本にする

Codexはリポジトリ内の`AGENTS.md`をプロジェクト指示として利用します。既存の`CLAUDE.md`から、ツールに依存しない有効な規則を移し、同じ規則を2つのファイルに複製して維持する運用を避けます。

ルートの`AGENTS.md`には、次の内容を簡潔に整理します。

1. **リポジトリの目的と構成**
   - 生成AI、機械学習、ソフトウェア開発などの学習成果を日付ディレクトリに記録すること。
   - 各作業ディレクトリに`README.md`または`work_log.md`を置く運用。
2. **変更・記録の進め方**
   - 作業を小さく区切り、結果や判断を文書に残すこと。
   - 既存のディレクトリ構成と説明を確認してから追加すること。
3. **Gitとファイルの扱い**
   - 変更前後に`git status`を確認すること。
   - 意図しない未追跡ファイルを放置せず、コミット対象を個別に選ぶこと。
   - 既存のGit運用方針に従い、push前に差分と対象ファイルを確認すること。
4. **秘密情報**
   - APIキーや認証情報をコミットしないこと。
   - `.env`の実体は共有せず、必要な場合は`.env.example`を使うこと。
5. **Web成果物と公開**
   - 静的サイトのホスティング判断は既存の基準と`260805/hosting_policy.md`を参照すること。
   - 公開ページや公開URLを追加・変更した場合はREADMEの一覧を更新すること。
   - `260805/hosting_policy.md`から共通のホスティング判断基準へのリンクを維持すること。
   - 公開を伴う変更は、差分と表示を確認してから既存の公開手順に進むこと。

`AGENTS.md`は全タスクで参照されるため、手順書や全プロジェクトの詳細を詰め込みません。詳細な運用資料は既存の関連ドキュメントに置き、ここから必要なものを案内します。

### 4.2 `CLAUDE.md`から共通指示を読み込む

実施後のルート`CLAUDE.md`は、共通指示のインポートと、必要な場合だけClaude Code固有の指示を置く構成にします。

```markdown
@AGENTS.md

<!-- Claude Code固有の指示が必要になった場合のみ、この下に追加する。 -->
```

現行のClaude Codeは`AGENTS.md`を読み込めますが、同じ階層または上位階層に`CLAUDE.md`がある場合、標準設定では`CLAUDE.md`だけが読み込まれます。そのため、両方を置く構成では明示的な`@AGENTS.md`インポートを残します。公式ドキュメントによると、このインポートは`AGENTS.md`を二重に読み込ませません。

Claude Codeで実施後に確認する項目は次のとおりです。

- `/context`で`CLAUDE.md`が読み込まれていること。
- `@AGENTS.md`の内容がClaude Codeのコンテキストに含まれていること。
- Claude Code固有のルールを追加する場合、共通ルールと重複・矛盾していないこと。

### 4.3 Codex側の確認

Codexでルートの`AGENTS.md`が適用されることを、文書変更を使った小さな作業で確認します。最初にCodexへリポジトリの目的、変更記録、秘密情報、公開前確認のルールを要約させ、`AGENTS.md`の内容と合っているか確認します。併せて、依頼したファイル以外に変更が広がっていないことを差分で確認します。

ユーザー全体のCodex設定や`~/.codex/config.toml`は、このリポジトリ移行のために変更しません。

## 5. 公開情報の表記変更

リポジトリのURLを保ったまま、現在の実態に合う中立的な表現へ整えます。Claude Codeを使った過去の出来事は、その歴史的記録として残します。

### 5.1 README

対象ファイル: ルートの`README.md`

- 見出しを`# AI & Software Practice`に変更する。
- 冒頭説明を、例えば次のようにする。

  > 生成AI・機械学習・ソフトウェア開発の学習記録と成果物を、日付ごとに管理するリポジトリです。

- GitHub PagesのURLと各公開ページのリンクは、リポジトリ名を変更しないため現行URLのままにする。
- 過去の各日付の説明にある「Claude Codeで作成」「Claude Designで実施」などの記述は、実際の制作経緯を示すので一括置換しない。
- 本計画へのリンクとして、ディレクトリ一覧の`261014`行を維持する。

### 5.2 GitHub Pagesトップページ

対象ファイル: ルートの`index.html`

- `<title>`を`AI & Software Practice — kenobix`にする。
- サイト名の表示を`kenobix / AI & Software Practice`にする。
- ヒーロー見出しを「生成AI・ソフトウェア開発」「学習・実践ログ」を中心とする説明に変更する。
- ヒーローの説明文を、複数分野の成果物と作業ログを日付ごとに記録する内容にする。
- フッターのサイト名をヘッダーと揃える。
- 過去の記録カードにあるClaude固有の説明は、制作実績として正確である限り残す。
- GitHubリポジトリへのリンク、既存の各ページへの相対リンク、`/Claude_practice/`を含む公開URLは変更しない。

### 5.3 GitHubのリポジトリ説明

GitHubのリポジトリ画面にあるAbout欄の説明も、Claude Codeだけを示している場合はツール非依存の説明に変更します。これはローカルファイルの編集ではなくGitHub上の設定変更です。変更する場合も、リポジトリ名は維持します。説明文の候補は「生成AI・機械学習・ソフトウェア開発の学習記録と成果物を公開しています。」です。

## 6. 実施手順

### フェーズ0: 作業前の状態を記録する

1. `git status --short --branch`で現在のブランチ、変更、未追跡ファイルを確認する。
2. 未追跡ファイルを一つずつ確認し、今回の指示ファイル・表記変更と混ぜない。
3. `README.md`、`CLAUDE.md`、`index.html`、`260805/hosting_policy.md`の現行内容を確認する。
4. この作業ではリポジトリ名、remote URL、Pages設定を変更しない。

### フェーズ1: 共通指示を整える

1. ルートに`AGENTS.md`を新規作成し、4.1の項目を現在有効な内容に即して記載する。
2. 現在の`CLAUDE.md`から有効な共通ルールを移す。古くなった記述や対象外の記述をそのまま移植しない。
3. `CLAUDE.md`を`@AGENTS.md`のインポートと必要なClaude固有ルールに整理する。
4. `260805/hosting_policy.md`の現行ルールへの参照を`AGENTS.md`に更新する。過去の作業記録など、当時のファイル構成を示す記述は変更しない。
5. Codexで小さな文書タスクを行い、`AGENTS.md`に従うことと差分の範囲を確認する。
6. Claude Codeも使う場合は新しいセッションで`/context`を確認し、インポートが反映されることを確かめる。

### フェーズ2: READMEとトップページを整える

1. READMEのタイトルと概要を5.1の方針に合わせる。
2. `index.html`のタイトル、ブランド表示、ヒーロー見出し・説明、フッターを5.2の方針に合わせる。
3. Claude Codeを使った過去の記録は保持し、機械的な一括置換を避ける。
4. GitHub Pagesのリンクとリポジトリリンクが現在のURLを指していることを確認する。
5. `260805/hosting_policy.md`の共通ルールへのリンクが`AGENTS.md`を指していることを確認する。
6. GitHub About欄を更新する場合は、その変更内容も記録する。

### フェーズ3: 差分レビューと公開

1. `git diff`と`git status`で変更ファイルを確認し、未依頼の変更が含まれていないことを確かめる。
2. ローカルでトップページを開き、タイトル・見出し・説明・リンク先を確認する。
3. READMEの公開ページ一覧と、トップページの主要リンクを照合する。
4. 秘密情報や不要な生成物がステージ対象に含まれていないことを確認する。
5. 内容のレビュー後、コミット・pushはユーザーの指示とリポジトリのGit運用ルールに従って行う。
6. pushして公開した場合は、GitHub Pagesのトップページと既存の公開先が引き続き開けることを確認する。

本計画の各作業は、依頼された範囲とユーザーの公開指示に従って進めます。公開を行う場合は、ローカル確認と差分レビューを終えてからpushし、公開後に既存URLを確認します。

## 7. 完了条件

- Codexがルートの`AGENTS.md`をプロジェクト指示として利用できる。
- Claude Codeを使う場合は、`CLAUDE.md`経由で共通指示を読み込める。
- 共通ルールが`AGENTS.md`に一元化され、2つのファイル間に矛盾した複製がない。
- READMEとPagesトップの概要が、現在の複数分野の活動を正しく表している。
- 過去のClaude Code関連記録が事実に沿って保持されている。
- リポジトリ名、GitHub PagesのベースURL、既存の公開ページURLが維持されている。
- 未追跡ファイルを含め、意図しないファイルがコミット対象になっていない。

## 8. 将来見直す条件

リポジトリ名を中立的な名前へ変更する場合は、候補名だけで決定せず、GitHub PagesのURL変更と外部共有済みリンクの影響を先に確認します。独自ドメインでURLを保つか、旧URLを使う外部リンクを更新するかを決めてから実施します。

個別の成果物を独立リポジトリにする場合は、別途、Git履歴の継承、README・Issue等の管理、Pagesのベースパス、依存関係とデプロイ方式、学習ログからのリンクを計画します。
