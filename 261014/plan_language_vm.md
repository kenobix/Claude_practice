# 企画: 小さな言語と、同じプログラムを動かす2種類の処理系

- 作成・見直し日: 2026-10-14
- 状態: **未実装の開発計画**。性能・一致性は今後検証する。
- 位置づけ: 言語の仕様化、木構造、状態、実行機構を深く学ぶ独立候補。
- 総合判断・他候補: [次のプロジェクトの選び方](next_project_plan.md)

## 目的と見直し判断

整数と真偽値を持つ小さな言語を設計し、構文木を直接評価するインタプリタと、命令列を実行するVMを作る。
同じ入力が同じ結果・エラーになることを確認し、処理の違いをトークン、AST、命令列、実行トレースから説明する。
利用者は、処理系の動きを学ぶ自分と、その仕組みを再現したい開発者を想定する。

元案の「言語とVM」は学習効果のある候補だが、型推論、JIT、GCまで一度に含めると完成条件が曖昧になる。
最初は関数・クラスを持たない言語で、仕様と実装の対応、エラー処理、二つの処理系の一致を成果にする。
実装言語はPythonを暫定候補とし、新しい実装言語の習得と処理系の設計を同時に抱え込まない。
Python上のVMがAST評価より速いとは仮定せず、計測結果とその理由を説明する。

## 最小完成範囲と後回し

MVPはCLI、字句・構文解析、明示的な型検査、AST評価、バイトコード生成、VM、逆アセンブル表示までとする。
学習の入口としてAST評価までを中間成果にし、二つの処理系の一致を示した時点を企画全体のMVP完成とする。
値は整数`int`と真偽値`bool`だけ、文は変数宣言・代入・出力・ブロック・分岐・反復に限定する。
関数、再帰、クロージャ、配列、文字列、モジュール、ファイル/ネットワークI/Oは後回しにする。
静的な型検査は明示注釈の照合までとし、型推論・ジェネリクス・JIT・独自GCは別の拡張にする。
数か月を使える場合も、文法を増やす前に現行仕様の一致性、診断、測定を完成させる。

## 言語仕様の初期案

UTF-8のソースを読み、識別子と構文記号はASCIIに限定する。コメントは`//`から行末までとする。
整数リテラルは10進数字列、真偽値は`true` / `false`、宣言には型と初期値を必須とする。
`IDENT`は`[A-Za-z_][A-Za-z0-9_]*`から予約語を除く。`INTEGER`は`[0-9]+`で、先頭ゼロも10進とする。
空白・タブ・改行は区切りとし、LF/CRLFを受け付ける。演算子は最長一致で読み、`//`は除算よりコメントとして扱う。
以下のEBNFをPhase 0で仕様ファイルに移し、変更時は例と期待値を同時に更新する。

```ebnf
program    = { declaration }, EOF ;
declaration= "let", IDENT, ":", type, "=", expression, ";" | statement ;
type       = "int" | "bool" ;
statement  = IDENT, "=", expression, ";"
           | "print", expression, ";" | block
           | "if", "(", expression, ")", block, [ "else", block ]
           | "while", "(", expression, ")", block ;
block      = "{", { declaration }, "}" ;
expression = equality ;
equality   = comparison, [ ( "==" | "!=" ), comparison ] ;
comparison = term, [ ( "<" | "<=" | ">" | ">=" ), term ] ;
term       = factor, { ( "+" | "-" ), factor } ;
factor     = unary, { ( "*" | "/" | "%" ), unary } ;
unary      = ( "!" | "-" ), unary | primary ;
primary    = INTEGER | "true" | "false" | IDENT | "(", expression, ")" ;
```

| 項目 | 規約 |
|---|---|
| 評価順 | 二項演算の左辺、右辺の順。加減乗除は同一優先度内で左結合 |
| 整数 | 任意精度の整数。ただし1値4096bitまでの実行資源上限を設け、超過は`E_LIMIT` |
| 算術 | `+ - * / %`はint同士だけ。`/`は床関数による整数除算、`a = (a / b) * b + (a % b)` |
| 真偽値 | boolをintに暗黙変換しない。`!`、if/while条件にはboolのみを許可 |
| 比較 | 大小比較はint同士、等値比較は同じ型同士。`1 < 2 < 3`等、同じ層の比較連鎖は文法エラー |
| 宣言と代入 | 型注釈は必須。初期値と代入値の型は宣言型に一致する必要がある |
| スコープ | ブロック単位のレキシカルスコープ。内側の宣言で外側を隠せるが同一スコープ再宣言はエラー |
| 名前参照 | 使用位置より前の最も内側の宣言に結び付ける。未宣言・宣言自身の初期値からの参照はエラー |
| 出力 | intは10進、boolは`true`/`false`で1行ずつ標準出力。暗黙の式結果表示はしない |
| 失敗 | 構文・名前・型エラーは実行前に検出。ゼロ除算は実行時、資源上限は超過を検出した段階で停止 |

負の除算は`-7 / 3 = -3`、`-7 % 3 = 2`と定義し、両処理系で同じ結果にする。
Pythonのboolが整数として扱える箇所をそのまま使わず、言語の値に型タグを持たせる。
整数のbit数は絶対値のbit長で判定する。リテラルの4096bit上限は共通フロントエンドで実行前に検査し、未実行の分岐内でも超過を入力/静的エラーとして扱う。演算結果の超過は両処理系で演算直後の実行時エラーとする。コンパイラだけが巨大定数を先に拒否する違いを作らない。
両分岐とループ本体を実行前に検査し、実際には通らない枝の型エラーも検出する。
初期値の自己参照は、外側に同名の変数があっても禁止する。
構文・静的エラー時は出力なし、実行時エラーではそれまでの出力を残し、以後の文を実行しない。
診断は`code / phase / message / line / column / span`を持ち、行・列を1始まりで表示する。
位置のspanはUTF-8バイト範囲、列は行頭からのUnicode文字数とし、タブは1文字として数える。
spanは開始を含み終了を含まない範囲とする。ゼロ除算と演算結果の上限エラーは演算子トークンの位置に固定し、コンパイル時に同じ位置を命令へ引き継ぐ。
最初は先頭の1エラーで停止し、終了コードは成功0、入力/静的エラー2、実行時エラー3、内部不具合4とする。

## 暫定構成と不変条件

```text
source → scanner → tokens → parser → AST → resolver/type checker
                                               ├→ AST evaluator → output
                                               └→ compiler → bytecode → VM → output
```

著者の原稿で示されるAST評価とバイトコード処理系の二段階を学習の参考にするが、実装言語や文法は本計画で定義する。[Crafting Interpreters公式リポジトリ](https://github.com/munificent/craftinginterpreters)
名前解決は構文解析後に行い、変数参照を宣言IDへ固定する。[著者原稿: Resolving and Binding](https://raw.githubusercontent.com/munificent/craftinginterpreters/master/book/resolving-and-binding.md)

将来の配置は`<開始日>/tiny_language/`とし、`scanner.py`、`parser.py`、`resolver.py`、`type_checker.py`、`interpreter.py`、`compiler.py`、`vm.py`に分ける。標準ライブラリの`types`と衝突するファイル名は避ける。
初期VMはスタック方式とし、定数、変数の読み書き、算術、比較、条件分岐、ジャンプ、出力、停止を命令にする。
各命令に入力スタック数・出力スタック数とソース位置を定義し、分岐の合流点でスタック深さが一致することを検査する。
変数は宣言IDに対応するスロットへ配置し、ループ内の宣言は各実行で初期値を格納し直す。
バイトコードは当面メモリ内でのみ生成・実行する。外部バイナリの読み込みや互換フォーマットは追加しない。
自作コンパイラの出力にも、不正命令・範囲外ジャンプ・スタック不足の検査を行い、内部不具合を診断する。
ホストの`eval`や`exec`へユーザーのソースを渡さず、値・制御を自分の処理系で実行する。
ソースサイズ、字句数、構文の深さ、出力行数、整数のbit数、実行ステップ数に上限を設ける。
ASTの評価回数とVMの命令数は異なるため、資源上限エラーが同じステップで起きるとは要求しない。

## 段階別の作業計画

### Phase 0: 仕様と実行例を固定 — 10〜16時間

文法・型・スコープ・演算・エラー・資源上限を`docs/language_spec.md`にまとめる。
手計算できる四則演算、合計ループ、分岐、shadowingと、各エラー例を作る。
**成果物:** 言語仕様、正常/異常の入力と期待出力、構成図。
**完了条件:** 同じサンプルについて二通りの解釈が残らず、仕様だけで期待結果を書ける。

### Phase 1: 字句・構文解析 — 14〜22時間

トークンに位置を保持し、再帰下降法でASTを生成する。演算子優先順位を文法の層に対応させる。
`--tokens`と`--ast`で中間結果を出し、コメント、改行、括弧、EOFを含む入力の診断を実装する。
**成果物:** scanner、parser、AST表示、ソース位置付き診断。
**完了条件:** 正しい構文が期待ASTになり、余分なトークン・欠落記号・上限超過が明確に失敗する。

### Phase 2: 名前・型検査とAST評価 — 18〜28時間

スコープのスタック、宣言ID、自己参照検査を実装し、演算・条件・代入の型を検査する。
評価器、ループの停止上限、資源制限、診断のCLI表示を実装する。
**成果物:** `run --engine ast`、実行仕様のサンプル集、設計判断の記録。
**完了条件:** 正常例と異常例が手計算に一致し、実行前エラーで出力が発生しない。ここが中間完成である。

### Phase 3: コンパイラとVM — 22〜34時間

命令一覧、スタック効果、ジャンプ先の規則を`docs/bytecode.md`へ記載する。
定数・変数・算術から実装し、if/whileの前方・後方ジャンプを追加する。
`--disassemble`と`--trace`で命令位置・スタック・変数を追跡できるようにする。
**成果物:** バイトコード生成器、VM、逆アセンブル、内部検査。
**完了条件:** Phase 2の全正常例がVMでも同じ出力を返し、静的エラーと実行時エラーの規約が保たれる。

### Phase 4: 一致性と性能を説明 — 14〜22時間

同じサンプル群を両処理系で動かし、出力・診断コード・ソース位置を照合する。
小さい値と有界ループで生成したプログラムも比較し、手書き期待値にない組み合わせを調べる。
計算ループ、分岐、変数アクセスを用意し、解析・型検査・コンパイル・実行の各時間を分けて記録する。
**成果物:** 一致性の結果表、計測条件、3分動画、README、既知の制約。
**完了条件:** 未説明の不一致がなく、クリーンな環境でサンプルを再現できる。ここをMVP完成とする。

### 深掘り: 完成後に一つ選ぶ — 追加24〜60時間

候補は、関数呼び出しとフレーム、バイトコード最適化、または同じ仕様の別実装言語への移植とする。
関数を選ぶ場合は、引数・戻り値・再帰の上限・スコープを先に仕様化し、クロージャはさらに後にする。
独自GCはホストのメモリ管理に任せたMVPとは別の到達点であり、ヒープ上の値と到達可能性を学ぶ段階で再計画する。
JITと型推論は独立企画に近い規模になり得るため、この工数に含めない。

## 検証計画と異常系

| ケース | 期待する挙動 |
|---|---|
| `print 1 + 2 * 3;` / 括弧付き | 優先順位に従うASTと値。両処理系で一致 |
| 負の除算・剰余 | 床関数による除算と剰余の関係式を満たす |
| `let x: int = true;` | 実行前に型エラー。出力なし |
| 未宣言・自己参照・同一スコープ再宣言 | 名前解決の段階で失敗 |
| ブロック内shadowing / 外側変数への代入 | 宣言IDに従って値が読み書きされる |
| 未実行分岐の型エラー | プログラム全体の実行前に失敗 |
| ゼロ除算 | 直前までの出力を残し、演算箇所で停止 |
| 無限ループ / 深すぎる式 / 巨大整数 | 指定した上限で診断して停止 |
| 不正ジャンプ・スタック不足 | VM内部検査の診断。Pythonの生の例外に任せない |

ASTとVMが同じ型検査器・演算関数を共有すると、両方が同じように間違う可能性がある。
そのため差分検証に加え、仕様から手計算した独立期待値と、演算の関係式を使う。
生成テストは小さい整数・有界ループに制限し、異なる資源上限に達した結果を意味上の不一致と混同しない。
性能は出力I/Oを除いた計算例でも測り、Pythonの版、CPU、入力、繰り返し回数、中央値を残す。
VMが遅い場合も結果を残し、命令dispatchや値の表現など、観測できた原因を切り分ける。

## 工数、削る順序、完成判断

学習・実装・不具合修正・資料化を含め、ASTまで**42〜66時間**、VMと比較を含むMVP全体は**78〜122時間**を見込む。
深掘りは追加**24〜60時間**。週8〜10時間なら全体MVPは約8〜16週という換算例であり、週の時間数は未確定である。
Phase 1終了時に構文解析の実績を基に再見積もりし、全機能の追加と新言語への移植を同時に進めない。
短縮時はWebプレイグラウンド、最適化、関数追加の順に見送り、中間完成のAST処理系を先に公開する。
VMを省いた場合は「言語インタプリタの完成」と明記し、「言語とVMの企画完了」とはしない。
仕様・位置付きエラー・上限制御・独立期待値・再現手順は残す。

## 3分デモと企業へ説明する証拠

0〜45秒で10行程度の合計プログラムを動かし、ソースと出力、ASTを対応させる。
45〜100秒で同じソースの命令列とVMトレースを見せ、条件分岐とスタックの変化を説明する。
100〜145秒で型の誤りとスコープの例を示し、実行前に検出する理由を説明する。
145〜180秒で一致性の結果、速度比較、未対応機能と次の判断を示す。
提出する証拠は文法・意味規則、命令仕様、サンプル、差分結果、測定条件、実装上の判断記録である。
説明の中心は「独自言語を作った」という名称より、曖昧な要求を仕様へ落とし、正しさを確かめた過程に置く。
