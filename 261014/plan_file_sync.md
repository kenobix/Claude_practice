# 2クライアントとハブで作るファイル同期ソフトの詳細計画

- 作成・資料確認日: 2026-10-14
- 状態: 企画・作業計画。以下の機能、検証、計測は未実施。
- 関連: [企画全体の比較と選び方](next_project_plan.md)
- 想定: 個人開発、LinuxまたはWSLのLinuxファイルシステム、人工データを使う。

## 1. 目的と企画の修正判断

2つの作業フォルダの更新を同期し、切断、再送、同時編集、削除の衝突が起きても、何が残り何を人が判断する必要があるかを説明できる道具を作る。対象利用者は、自分の複数環境を同期したい開発者と、分散状態の設計を学ぶ人である。

元案は学習効果と実演の分かりやすさを備える。ただし最初からP2P、差分転送、暗号化、競合解決、複数OSを含めると完成が遠い。最初は**2クライアント＋中央ハブ、ファイル単位の全量転送、競合は両方保存**に修正する。これは中央ハブに依存する同期ソフトであり、完全な分散P2Pと紹介しない。

既存の[ブロックチェーン作業ログ](../260702/work_log.md)には同期の学習があり、[node.py](../260702/blockchain/node.py)は実ネットワークを使わず、同一プロセス内でノードを同期する。今回新しく扱うのは、別プロセス間の通信、ファイルの永続状態、再接続、削除記録、競合の保存である。主要コード・ログの確認範囲で同種のファイル同期実装は見当たらない。

企業への説明材料は、同期中の通信断や同時編集を再現し、無言で上書きしない設計を根拠付きで示すことに置く。バックエンド、デスクトップ、基盤分野との接点があるが、既存同期製品を上回ることや採用上の効果は保証しない。

本人は広いソフトウェア開発力とAI・MLエンジニアの両方を重視し、数か月以上の深掘りも可能と回答している。本案は通信と永続状態の基礎を学ぶ独立候補である。AI・MLとの接続には小さな実験設定・評価結果の同期例を使えるが、大規模データセットやモデル配布への対応は別工程とする。

## 2. 最小完成範囲と対象外

| 項目 | 最初の完成範囲 |
|---|---|
| 構成 | ハブ1プロセス、クライアント2プロセス、同期フォルダ各1つ |
| ファイル | 通常ファイル、相対パス。1ファイル10 MiB以下、合計1,000ファイル以下を暫定上限 |
| 操作 | 作成、更新、削除、`scan`、`sync-once`、`status`、競合確認 |
| 通信 | localhostのHTTPと登録済みclient ID・認証トークン。LAN実験前にTLSを設定 |
| 整合性 | ハブの版番号、CAS、削除記録、操作IDによる再送の重複排除 |
| 保存 | ハブのblobとSQLite、各クライアントのローカル同期状態 |
| 利用条件 | 同期実行中の外部編集は一旦止める。編集を続けながら同期する常駐版は拡張 |

上限は生存ファイル数だけでなく、一時ファイル、旧blob、競合コピー、削除記録にも適用する。ハブの総保存量は暫定2 GiBを上限とし、到達前に新規更新を拒否して既存状態を維持する。実演データは合計100 MiB以下から始める。

初期対象はLinux同士とし、Windows側のマウント領域、ネットワークファイルシステム、symlink、hard link、特殊ファイル、権限・所有者・拡張属性・空ディレクトリの同期を除外する。名前変更は「旧パスの削除＋新パスの作成」と扱い、原子的なrenameとして伝播しない。

P2P、ベクトル時計、差分転送、自動マージ、スマートフォン、GUI、インターネット公開、複数ハブ、E2EEは後回しにする。同期は削除も伝播させるため、長期バックアップを代替する機能として扱わない。

## 3. 暫定スタックと構成

GoのCLI・HTTPサーバー、SQLiteのメタデータ、通常ファイルのblob保存を暫定候補とする。既存の[SQLite利用経験](../260406/dashboard/README.md)をメタデータ保存に使い、同期状態の判断に時間を割く。バージョンとSQLiteドライバは着手時に固定する。

```text
フォルダA ← Client A → Hub API ← Client B → フォルダB
              ↓          ↓          ↓
          ローカル状態  SQLite    ローカル状態
                         ＋
                    内容hash別blob
```

自作するのは差分判定、版比較、CAS更新、再送・競合・削除の状態遷移である。HTTP/TLS、SHA-256、SQLite、OSの安全なファイル操作を既存実装に任せる。暗号方式やSQLite自体を自作する計画ではない。

実装は着手日ディレクトリの`file-sync/`へ置き、`cmd/hub/`、`cmd/client/`、`internal/protocol/`、`internal/reconcile/`、`docs/`を分ける。実演用のA・B・ハブ領域は一時ディレクトリに作る。

## 4. データ契約と競合規則

### 4.1 メタデータとAPI

ハブは`path / revision / content_hash / size / deleted / client_id`を保持する。`revision`はパスごとに増加し、削除してもリセットしない。クライアントは最後に同期した版とhash、送信待ち操作ID、競合状態を永続化する。mtimeは版の新旧判定に使わない。

各同期フォルダはOSの排他ロックで1クライアントだけが操作する。SQLiteはWALと`synchronous=FULL`を明示し、起動時に実際の設定を確認する。manifestは読み取りトランザクションで一貫したスナップショットとして返す。

| API案 | 契約 |
|---|---|
| `GET /v1/manifest` | 削除記録を含む全メタデータとハブ世代IDを返す |
| `PUT /v1/blobs/{hash}` | サイズ・SHA-256を検証した内容を保存。同じhashの再送を許可 |
| `GET /v1/blobs/{hash}` | 内容を取得。受信側でもhashとサイズを照合 |
| `POST /v1/changes` | `hub_generation / client_id / op_id / path / base_revision / hash / deleted`を受け取る |

`changes`は現在版が`base_revision`と一致する場合だけ更新するCASとする。新規パスは版0を期待する。版不一致は409と最新メタデータを返し、黙って新しい版を上書きしない。ハブはSQLiteトランザクション内で、版確認、更新、操作結果保存を一括で行う。

`(client_id, op_id)`には一意制約を設け、同じ内容の再送には以前の結果を返す。異なる内容で同じIDを使った場合はエラーにする。クライアントは送信前に操作IDと内容を保存し、応答消失後も同じIDで再試行する。再判断して別の操作を送る場合は新しいIDを作る。

### 4.2 競合と削除

- ローカル未変更・ハブ更新済みなら、ハブの内容を受信する。
- ローカル変更済み・ハブが基準版のままなら、CASで送信する。
- 両方変更済みなら、ローカル内容を予約済み管理領域へ競合コピーとして保存し、元パスへの反映を保留する。
- 競合一覧はローカル版・検出時のハブ版・共通の基準版を示す。検出時のhashを保存して両内容を参照可能に保ち、人が選んだ内容を最新のハブ版に対する新規CAS操作で反映する。
- 削除はファイル行を消す操作にせず、`deleted=true`のtombstoneとして版を増やす。
- オフライン端末の未変更な旧ファイルは再接続時に削除を受け入れる。旧版を編集していた場合は削除との競合として保存する。
- tombstoneと操作ID履歴はMVPでは自動削除しない。長期オフライン端末による削除ファイルの復活を防ぐためである。
- ローカル状態を失った端末やハブ世代IDが変わった場合は、自動アップロードを止める。新規参加としてmanifestと内容を照合し、明示的に再登録する。
- 通常再起動ではハブ世代IDを維持し、バックアップからの復元手順では必ず新しい世代IDを発行する。巻き戻った版番号だけで旧端末のCASが通らないよう、更新要求にも世代IDを必須にして不一致を拒否する。

ローカルのファイル不存在を削除として送れるのは、以前に同期済みと記録されたパスに限る。初回参加は「空のフォルダへ受信」または「空のハブへの初回登録」を明示して開始する。通常ファイル`a`とその配下の`a/b`を同時に持つような名前空間衝突も拒否し、既存内容を保持する。

Syncthingの仕様にも削除フラグと版情報があり、ユーザー向け文書では競合コピーと一時ファイルを説明している。本計画の中央CAS方式は独自の簡略化で、Syncthingのプロトコル互換を目標にしない。[BEP仕様](https://docs.syncthing.net/specs/bep-v1.html)、[同期動作の説明](https://docs.syncthing.net/users/syncing.html)

### 4.3 ファイルとDBの更新順序

ハブはblobを一時ファイルに書き、hash照合・ファイル同期・同一ファイルシステム内へのrename・親ディレクトリ同期を済ませてから、SQLiteへ参照を登録する。これによりDBが未完成blobを参照する順序を避ける。CAS失敗で生じた未参照blobはMVPでは削除せず、容量を記録する。

受信側も一時ファイルへ書き、hash照合・ファイル同期後に反映する。置換前のローカル状態を再確認し、変化があれば競合として止める。反映予定をローカルDBに記録し、同一ファイルシステム内のrename・ディレクトリ同期後に同期済み版を更新する。途中停止後は予定と実ファイルのhashを照合して完了・再試行・競合を決める。

ファイルとSQLiteの更新を単一トランザクションだと仮定しない。削除時も同じ反映予定を記録し、直前の内容を管理領域に退避してから元パスを削除する。復旧時の「ファイルなし」を新たな利用者の削除と取り違えない。

外部エディタとの競合を完全に止めるには協調が必要なため、MVPは同期中の編集停止を利用条件とする。前後のhash確認だけで、あらゆる書き換え競合に対する無損失を保証したとは扱わない。

### 4.4 パスと認証の境界

絶対パス、`.`・`..`の要素、空要素、NUL、バックスラッシュ、管理領域名、symlink・特殊ファイルを拒否する。パスを清掃して許可するのではなく、受け付ける形式を明示する。Linux上でもUnicode正規化や大小文字の同一視は行わず、対応文字列と上限をプロトコル仕様に記載する。

ディレクトリ内のパス検査後にリンクを差し替える競合も考慮し、ルート配下に操作を制限するAPIを使う。Goの`os.Root`などの利用可能な操作は着手時の標準ライブラリ仕様で確認する。[Go: Traversal-resistant file APIs](https://go.dev/blog/osroot)

ハブは登録済み端末と同期領域を対応させる。blobのhashを知っているだけで他領域の内容を取得できる認可にしない。認証トークンは環境変数またはGit管理外の設定へ置き、本文・ログへ出力しない。

## 5. 段階別の作業計画

### 段階0: 状態と利用条件を固定する（10〜16時間）

- 同期対象、パス規則、版、操作ID、端末再登録、容量上限を定義する。
- 同時編集、編集対削除、オフライン中の削除、応答消失の状態表を作る。
- 成果物: `docs/protocol.md`、状態遷移図、利用条件、デモ用ファイル一覧。
- 完了条件: 各状態で、送信・受信・保留のどれになるか一意に決まる。

### 段階1: 安全な走査と1方向コピーを作る（16〜24時間）

- `scan`で通常ファイルの相対パス、サイズ、hashを収集する。
- ローカルのAからBへ一時ファイルを経由してコピーし、異常時の中止を作る。
- 成果物: 走査器、パス検証、hash照合、反映予定と再起動処理。
- 完了条件: 途中コピーを完成品として扱わず、対象外パス・ファイルを理由付きで拒否する。

### 段階2: ハブ経由の正常同期を通す（20〜30時間）

- blob API、manifest、SQLite保存、CAS、操作IDの重複排除を実装する。
- Aで作成し、ハブを経由してBへ届く`sync-once`を作る。
- 成果物: 3プロセスでのデモ、プロトコルのサンプル、状態表示。
- 完了条件: 再起動後にも版が残り、同一操作を繰り返しても版が二重に増えない。

### 段階3: 双方向の競合と削除を扱う（24〜38時間）

- 同時編集時の409、競合コピー、競合一覧、手動解決を実装する。
- tombstone、端末再接続、ローカル状態消失時の再登録を作る。
- 成果物: 編集対編集・編集対削除のデモ、削除復活を防ぐ検証ケース。
- 完了条件: どちらの変更内容も確認でき、古い端末が戻っても削除を通常更新として覆さない。

### 段階4: 通信・保存の障害を実験する（24〜38時間）

- upload中断、commit後の応答消失、ハブ停止、受信反映中の停止を注入する。
- 容量不足、壊れたblob、認証失敗、パス境界の検証を行う。
- 成果物: 操作ID・版・hashを追跡できるログと障害実験表。
- 完了条件: 再送で別の変更が生じず、完成していない内容で既存ファイルを置換しない。

### 段階5: 実演・計測・文書化を仕上げる（16〜24時間）

- ファイル数とサイズを変え、走査時間、転送量、収束時間を記録する。
- 自己所有の実機2台で試す場合はTLS・認証を設定し、同じ人工データを使う。
- 成果物: 起動手順、3〜5分のデモ、方式比較、既知の制限、再現コマンド。
- 完了条件: 第三者が2フォルダとハブを起動し、正常同期・競合・復旧を再現できる。

## 6. 実装時に行う検証・実験

| ケース | 合格とする結果 |
|---|---|
| A作成→B更新→A受信 | 両者とハブの版・hashが一致する |
| 同じ基準版からA・Bが別内容を送信 | 片方のみCAS成功。もう片方は競合として内容が残る |
| A削除中にBがオフライン→B再接続 | 未編集なら削除に収束し、編集済みなら競合となる |
| ハブcommit後に応答だけ破棄 | 同じ操作IDの再送が元の結果を返す |
| upload・download途中で停止 | 未完成blobがmanifestに出ず、受信先の旧内容が残る |
| rename後・ローカルDB更新前に停止 | 反映予定とhashから復旧し、自分の受信を再送しない |
| ローカルDB削除・古い状態へ復元 | 自動送信を止める、または版不一致を保留し、削除を復活させない |
| ハブを過去のバックアップへ復元 | 世代IDを更新し、古い世代の要求を拒否して再照合を要求する |
| `../`、絶対パス、symlinkの差し替え | 同期ルート外へ書き込まず、理由付きで拒否する |
| サイズ上限、hash不一致、容量不足 | 成功と表示せず、再試行可能性と保留理由を残す |

通常同期と障害時を分け、ファイル数・総容量・ネットワーク条件・試行回数・OSを記録する。性能は全量転送の基準値として測り、差分転送がないことを隠して他製品と速度比較しない。

## 7. 見積もり・範囲を削る順番・拡張

学習、実装、検証、文書化を含む合計は**110〜170時間**を暫定見積もりとする。週8〜10時間なら約11〜22週という換算例になり、実際の週当たり時間は未確定である。Go・ファイルI/O・ネットワークが初めてなら追加学習を見込み、段階2の終了時に見直す。

最初の判断点は段階2までの46〜70時間とする。削る順番は実機LAN実演、性能条件の数、表示の見栄えとする。CAS、tombstone、競合保存、パス境界、途中停止時の復旧は同期の中核なので削らない。

段階5までを満たした時点でMVPは完成とする。常駐化は次の独立した段階とし、監視イベントの重複・取りこぼしを再走査で補う。連続編集下でのローカル反映と編集の競合を改めて設計し、必要なら管理下の編集APIを導入する。ファイル監視だけで正しさを保証しない。[Syncthingの走査・監視の説明](https://docs.syncthing.net/users/syncing.html)

常駐化・停止再開・編集競合の対応には追加40〜80時間を仮置きする。全体150〜250時間、週8〜10時間の換算で約15〜32週が数か月以上取り組む場合の一例になる。段階4の実験結果から前提と追加時間を更新してから着手する。

その後に差分転送、tombstone回収、P2Pの順で検討する。tombstone回収には登録端末のackと退役・再登録の規則が必要で、経過日数だけで削除しない。P2P化する場合は中央の版番号とCASをそのまま使えないため、ベクトル時計などの因果関係の表現から別設計とする。

## 8. デモ・公開・費用・一次資料

公開する成果は、正常同期よりも「2台が別々に編集→競合を検出→両内容を確認」「片方を切断→他方で削除→再接続しても復活しない」の実演を中心とする。設計図、状態表、障害ログ、失敗した案と修正理由を添えれば、判断過程を説明できる。

MVPは手元の3プロセスで動かし、有料API・クラウド契約は不要。デモ用データと小さなfixtureだけをGitに残し、実フォルダ、blob、SQLite、トークンを除外する。静的な説明ページは[共通方針](../AGENTS.md)に従いGitHub Pagesへ置ける。常時稼働ハブの公開は、認証・保存容量・費用・運用担当を決める別の工程とする。
