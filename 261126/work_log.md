## 2026-11-25 Phase 0

### 計画と開発環境

着手時の作業ブランチは `feat/language-vm`。作業ツリーに未コミットの変更はなく、開始点の `0552746d3ed3596ac9bdeee737a17f9fde85a284` はリモートの `main` と一致した。 [元計画](../261014/plan_language_vm.md)・[開発の進め方](../docs/engineering/development-workflow.md)

元計画の段階構成を採用した。共通の字句・構文解析と静的検査を使うことで、AST評価とVM実行を同じ言語仕様で比較できる。AST評価を中間成果とし、VM、処理系間の比較、性能測定までをMVPとする。工数は元計画の見積もりを出発点とし、Phase 1終了時に実績を基に見直す。

開発環境はLinux x86_64、CPython 3.12.3、Git 2.43.0、GitHub CLI 2.102.0。標準ライブラリの `venv` でパッケージを追加せず一時環境を作り、`unittest` を起動した。実装とテストはPython 3.12の標準ライブラリで進める。実行時に依存する外部サービスはない。

### Phase 0で決めたこと

| 項目 | 判断と根拠 |
| --- | --- |
| 入力と診断 | 字句解析を完了してから構文解析に進み、名前解決を完了してから型を検査する。段階内の走査順と、コードごとの診断位置を定めた。同時に複数の誤りがあっても、最初の1件の期待値を決められる。 |
| 整数 | 元計画の4,096ビット上限を採用した。最大値の10進表記は1,234桁で、開発環境の既定の文字列変換上限は4,300桁だった。先頭ゼロを含むリテラルや、Python側の変換上限の設定が異なる環境でも言語仕様に従うように実装する。 [Python 3.12の整数変換上限](https://docs.python.org/3.12/library/stdtypes.html#integer-string-conversion-length-limitation) |
| その他の資源上限 | ソースを65,536バイト、トークンを8,192個、構文の深さを64、出力を1,024行、実行を100,000ステップとした。深さは括弧などの入れ子と構文木の両方を検査する。値はMVPで使う初期設定であり、性能測定に基づく値ではない。 |
| 実行ステップ | ASTは文や式のノードへの進入、VMは命令を数える。終了ステップと診断位置は各処理系の規則で確かめる。それ以外の出力と診断位置は共通の期待値を使う。 |

## 2026-11-25 Phase 1

### 実装

Phase 0の承認後、`feat/language-vm` の `8ac47e4` から作業を始めた。ソースは上限より1バイト多い65,537バイトまで読み、サイズ検査の後にUTF-8としてデコードする。字句解析器は改行とコメントを含む元のバイト列を基準にトークンのバイト範囲を求める。

再帰下降パーサーでは文法の階層ごとに式を組み立てる。括弧、単項演算子、ブロックに入る前に入れ子の深さを検査し、ASTの深さはノードを組み立てるたびに検査する。演算子と文の先頭トークンは、後続段階で診断位置に使えるようASTに残した。

整数リテラルは先頭ゼロを取り除き、残りを短い桁列ごとに整数に変換する。これによりPython側の10進変換上限にかかわらず、言語仕様の4,096ビットで判定できる。CLIはトークン、AST、診断をJSONで表示し、ASTの整数値は10進文字列にした。

### 検証と次の作業

Phase 0の入力と期待値を使い、正常系・異常系・境界条件の自動テスト23件を実行した。字句・構文解析の診断、先頭ゼロ付きの整数、上限直前・上限ちょうど・上限超過を確認し、Phase 1の受入条件を満たした。日本語文書は `yomiyasu` で検査し、検査後に最終稿を照合した。仕様上の条件と実装の対応は、コードとテスト結果でも確かめた。 [受入記録](docs/acceptance.md#phase-1の受入記録)

次のPhase 2では名前解決、型検査、AST評価を実装する。宣言IDへの結び付け、実行前エラーで出力が空であること、実行時エラーでそれまでの出力が残ることをPhase 0の期待値と照合する。

## 2026-11-25 Phase 2

Phase 1の承認後、`feat/language-vm` の `1b8c7d8` から作業を始めた。名前解決器は宣言を見つけた順にIDを割り当て、参照と代入先をIDに結び付ける。初期化中の名前を現在のスコープに登録してから式をたどるため、外側に同名の変数がある場合も自己参照を検出できる。型検査はプログラム全体の名前解決が終わってから行う。

AST評価器は宣言IDに対応するスロットに型付きの値を保持する。ブロックに入り直して宣言を実行すると、初期値でスロットを書き直す。整数リテラルの読み取りと10進出力は短い桁列に分けて変換する。`run --engine ast` は成功した `print` ごとにLFを付けて出力するため、後続の実行時エラーが起きてもそれまでの出力が残る。

固定例16件と境界入力を仕様から求めた期待値と照合し、Phase 1の回帰を含むテスト44件が成功した。共通資料に従い、境界値の直前、境界値、超過を確認した。日本語文書は `yomiyasu` の検査と最終稿の照合を行い、技術的な記述を実装とテスト結果に照らし合わせた。 [受入記録](docs/acceptance.md#phase-2の受入記録)・[テストと信頼性](../docs/engineering/testing-and-reliability.md)

専用CIを追加し、対象パスの変更でPython 3.12の全テストが走るようにした。次のPhase 3では命令のスタック効果、ジャンプ先、ソース位置を定義し、コンパイラとVM、逆アセンブルとトレースを実装する。
