# Phase 2の保存と復旧

Phase 2ではアプリの通信プロトコルを版2にし、コミット済みの操作を通知する `ACK` を追加した。既存のバイナリエンベロープとYjs更新形式V1は維持する。 [Phase 1の通信仕様](phase1-protocol.md)・[MVPの仕様・設計](design.md)

## SQLiteのデータ

| テーブル | 主な項目と用途 |
| --- | --- |
| `documents` | 文書ID、タイトル、所有者、状態、権限版、最新の受理順番号、作成日時 |
| `grants` | 文書と利用者の組、ロール、付与版、変更日時 |
| `updates` | 文書と受理順番号の組、正式なYjs状態を変えたバイナリ更新 |
| `receipts` | 文書・利用者・送信元・メッセージの組、受信バイト列のSHA-256、受理順番号、受理日時 |
| `snapshots` | 文書ID、包含した受理順番号、Yjsの完全状態、作成日時 |

SQLiteは単一プロセスで開き、`journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON` を使う。起動時はスナップショットと後続の更新ログから本文を再構築し、受理順番号と依存関係を検査する。ロードが完了してからHTTPとWebSocketの接続を受け付ける。共有DBの操作結果が不明になった場合は既存接続を閉じ、DBを開き直してすべての文書の状態を再構築する。再構築に失敗した場合は、認証を通過した文書への要求にHTTP 503を返す。 [SQLiteのWAL](https://www.sqlite.org/wal.html)・[SQLiteの同期設定](https://www.sqlite.org/pragma.html#pragma_synchronous)

## 更新と保存確認

1. サーバーは `UPDATE` のセッション、ロール、付与版、サイズ、頻度を検査し、受理記録を調べる。
2. 新しい操作は文書のコピーへYjs更新を適用する。依存待ちや形式の不備で拒否した操作は配信しない。
3. Yjs状態が変わった場合は、更新ログ、新しい受理順番号、受理記録を同じトランザクションでコミットする。状態が変わらない場合は現在の番号で受理記録だけをコミットする。
4. コミット後に正式状態を反映し、変更があった場合は送信元を含む全購読者に `APPLIED` を送る。送信元には `client_id`、`message_id`、`sequence` を含む `ACK` を返す。

再送時に同じ操作キーとハッシュが見つかれば、記録済みの順番号で `ACK` を返す。同じキーでハッシュが異なれば `MESSAGE_ID_CONFLICT` を返す。重複再送で更新ログや受理記録、配信を増やさない。

初期設定では文書ごとに100件の状態変更を受理するごとにスナップショットを作る。スナップショットと包含済みログの削除は同じトランザクションで確定する。次の更新の受理はその処理が終わってから行う。受理記録は残すため、ログ整理後も元の `ACK` を返せる。

## 端末の保存と再送

IndexedDBはアカウント別に作り、端末の送信元IDを保持する。Yjs状態と送信待ち更新は文書IDと付与版で管理する。ローカル編集を両方のストアへ同じトランザクションで保存し、完了後に送信する。1件ずつ送信し、保存確認が届かなければ同じIDとバイト列で再送する。対応する `ACK` が届いた場合に限り、その項目を送信待ちから削除する。後続の編集が残る間は「サーバー保存待ち」を表示する。 [IndexedDBの仕様](https://www.w3.org/TR/IndexedDB/)

同じ操作の `ACK` を送信ごとに2.5秒待つ。2回までは同じIDとバイト列で自動再送し、3回連続でタイムアウトした場合は保存確認が届かない旨を表示して接続を閉じる。送信待ちと端末内の状態を保持し、ページを開いたまま「接続し直す」で再送できる。停止した接続の遅延応答やタイマーは後続の接続で処理しない。`RATE_LIMIT` は応答として数えるため、タイムアウトの連続回数を戻し、350 ms待ってから再送する。権限エラーは受信時点で失効の手順に進む。 [権限と同期エラー](phase3-access.md#更新拒否と復帰)

復帰時は認可済みの `STATE` に端末の保存状態と残っている送信待ち更新を合成する。保存状態が欠けていれば、サーバーの状態と送信待ち更新から復元する。送信待ちの一部が欠けている場合は、サーバーの状態に残った送信待ち更新だけを適用した結果と、合成した状態を比較する。差分、依存待ち、欠けた受理確認があれば、新しいIDで補完更新を先に送る。既存の送信待ち更新には元のIDを使い、それぞれの `ACK` を確認する。削除だけの編集や、サーバーに反映されていて確認が届かなかった編集も確認対象に含める。 [Yjsの更新仕様](https://docs.yjs.dev/api/document-updates)

接続状態、端末内保存状態、サーバー保存状態は別々に表示する。初期状態の受信時点では「サーバー保存済み」を表示しない。現在の編集に対応する `ACK` がそろい、端末内の書き込みと送信待ちがなくなった時点で表示する。 [受入結果](acceptance.md#phase-2の受入結果)

Phase 3では送れなくなった付与版の下書きを端末に隔離する。削除済みの文書や失効した付与版からの更新は、受理記録を確認する前に拒否する。 [Phase 3の権限、削除、同期エラー](phase3-access.md)
