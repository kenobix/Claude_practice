# Phase 4のデモと性能計測

## デモ動画と再現手順

動画は実際のNode.jsサーバーと独立したChromiumプロファイルをPlaywrightで操作して収録した。字幕は操作と観測結果を説明する。共同編集では左が所有者のアキ、右が編集者のレン。右側の通信だけをテスト用のWebSocket中継で切断する。保存状態は画面に表示された値を使い、旧権限による拒否は同じセッションの試験用接続で実際の `ERROR` を確認した。書き出しの場面ではダウンロードしたUTF-8ファイルの内容をブラウザで表示する。

動画と性能値の取得対象は `cd29c34e86eb34cc5e302f44b3054c7936b2ff4d`。独立レビュー後の修正では改行と切断通知が届かない場合の回帰試験を追加した。動画と生データは取得時点の記録として扱う。 [再検証の結果](acceptance.md#独立レビュー後の再検証)

### ブラウザで手順をなぞる

1. [READMEの起動手順](../README.md#アプリを起動する)でサーバーを起動し、アキとレンを別プロファイルでログインさせる。アキが文書を作成し、レンを編集者にする。レンは一覧を更新して文書を開く。
2. 左右の画面で交互に編集し、本文と受理順番号がそろうことを確認する。同時挿入と削除の順序を制御する場合は、自動試験 `phase1.spec.ts` を使う。
3. レンのブラウザだけを開発者ツールからオフラインにする。アキが「資料を準備」、レンが「候補日を確認」を追記する。レンの通信を戻して「接続し直す」を押す。両端末の本文と番号が一致し、レンの保存確認が届く。
4. レンを再び切断して「端末だけの下書き」を追記し、アキがレンを閲覧者に変更する。レンが接続し直すと現在のサーバー本文が表示される。「同期を停止した下書き」からテキストを書き出して追記を確認する。旧付与版の拒否コードは `phase3.spec.ts` とサーバー試験、または録画用コマンドで再現できる。
5. 保存確認後にサーバーを停止し、同じDBで起動する。新たに表示されたパスワードでログインし、本文と順番号を確認する。

Chromiumの開発者ツールでオフラインを選んでも、既存WebSocketが残る場合は自動デモで再現する。動画を作り直す場合はFFmpegと日本語フォント（Noto Sans CJK JP）を用意し、`261125/app` から新しい出力ディレクトリを指定する。デモのデータと操作順は固定し、計測の入力生成にはseed `261125` を使用した。YjsのクライアントIDは実行ごとに変わるため、同時挿入の並び順は変わる場合がある。

編集画面のロールは再接続時の `STATE` で切り替わる。文書一覧に表示されるロールは「一覧を更新」で取り直す。

```bash
demo_root=$(mktemp -d)
npm run demo -- "$demo_root/recordings"
```

## 入力試験

Chromium DevTools Protocolの `Input.imeSetComposition` で「にほん」「日本」の合成イベントを発生させ、`Input.insertText` で確定した。絵文字、Enterによる改行、クリップボードからのキー操作による貼り付けを続け、両プロファイルで同じ本文を確認した。別試験では先に入力したアキがUndoを実行し、レンの「相手」が両端末に残った。 [Chromium入力のAPI](https://chromedevtools.github.io/devtools-protocol/tot/Input/)・[入力試験](../app/tests/phase4.spec.ts)

隔離したX11環境でuim/AnthyとIBus/Mozcを試したが、起動したChromiumに変換結果が届く経路を確立できなかった。その後、利用者がWindowsの日本語IMEで変換と確定を手動で確認した。 [手動確認の対象と結果](acceptance.md#windowsでの日本語imeの手動確認)

### OSの日本語IMEを手動で確認する手順

1. 日本語IMEが利用できるGUIブラウザで、アキとレンを独立したプロファイルにログインさせ、同じ文書を開く。
2. アキの本文欄で日本語入力を有効にし、`nihon` を入力する。候補から「日本」を選び、Enterで確定する。
3. 両画面で「日本」と同じ受理順番号が表示され、アキに「サーバー保存済み」が表示されることを確認する。OS、IME、ブラウザのバージョンと結果を記録する。

## 性能計測

### 環境と負荷

個別の一時SQLite DBとChromiumプロファイルを試行ごとに用意する。seed `261125` のASCIIデータを使い、初期本文1,024 UTF-16コード単位に、1件16コード単位の更新を100件追加する。キー入力の後に110 ms待つ。オンライン時の最終本文は2,624コード単位。続けて片側を切断し、双方で5件ずつ追加する。再接続後は両画面で本文2,784コード単位、受理順番号111を照合する。

Ubuntu 24.04.4のWSL 2上で、AMD Ryzen 7 7735HSの8論理CPU、Node.js 22.22.2、SQLite 3.51.2、Playwright 1.65.1、Chromium Headless Shell 159.0.8154.6を使用した。2026年11月26日17:04（日本時間）に、実装コミット `cd29c34e86eb34cc5e302f44b3054c7936b2ff4d` で計測を始めた。同じホストで録画・動画変換も動いたため、その負荷による影響も含み得る。

### 指標と観測位置

| 指標 | 開始と終了 |
| --- | --- |
| 更新配送 | Aの `UPDATE` を計測プロセスのWebSocket中継が観測してから、B宛ての同じ順番号の `APPLIED` を観測するまで |
| 保存確認 | 同じ `UPDATE` の観測から、A宛ての同じ操作IDの `ACK` を観測するまで |
| 再同期 | Bの「接続し直す」を押す直前から、A宛ての最後の `APPLIED`、B宛ての最後の `ACK`、両画面の本文・番号とBの保存表示を確認した時点までをそれぞれ計測 |
| 送受信量 | 両プロファイルのアプリのバイナリメッセージ長を方向別に合計。アプリヘッダー、`STATE`、`APPLIED`、`ACK`、`AWARENESS` を含む。WebSocketの下位フレーム、HTTP、TCPのバイトは含めない |
| DB増加量 | 初期投入後から100件の受理後までの差。SQLiteの論理ページ数とページサイズの積、および稼働中のメインファイルとWALの見かけのバイト数を記録 |

経過時間は計測プロセスの単調増加時計 `performance.now()` の差を使う。UTCは試行開始の記録に使う。更新配送・保存確認は500標本、切断復帰は5標本。中央値は昇順中央の値で、偶数なら中央2値の平均。p95は昇順の `ceil(0.95 × n)` 番目なので、5標本では最大値になる。中継とブラウザ操作を含むローカルの観測で、ネットワーク単体の遅延や製品の性能目標には使わない。

### 計測結果

| 観測 | 標本数 | 中央値（ms） | p95（ms） |
| --- | ---: | ---: | ---: |
| オンラインの更新配送 | 500 | 11.69 | 22.33 |
| オンラインのACK | 500 | 11.46 | 21.63 |
| 再接続から相手宛ての最終APPLIEDまで | 5 | 227.42 | 366.28 |
| 再接続から送信側の最終ACKまで | 5 | 228.96 | 368.69 |
| 再接続から両画面の本文と保存表示の確認まで | 5 | 377.75 | 466.99 |

オンラインの100件では1試行あたりAが17,600バイト送信し20,188バイト受信した。Bは送信0バイト、受信6,894バイトだった。再接続区間のAは送信0〜215バイト、受信451バイト、Bは送信977〜978バイト、受信4,070〜4,364バイトだった。オンライン100件の受理後、SQLiteの論理サイズは全試行で53,248バイト増加した。稼働中のメインファイルとWALの合計は2,257,760〜2,286,600バイト増加した。WALの計測値にはチェックポイント前の領域が含まれる。全試行で再接続後の本文が収束し、受理順番号111と保存確認を得た。
