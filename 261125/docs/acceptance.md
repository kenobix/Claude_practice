## Phase 1からPhase 4の必須試験

| ID | フェーズ | 操作と観測する結果 |
| --- | --- | --- |
| P1-1 | オンライン編集 | 所有者が文書を作成し、編集者と閲覧者を割り当てる。別ブラウザプロファイルの3端末で接続し、同じ位置への同時挿入と削除を行う。配送後の本文と配信の最終連番が全端末で一致する。閲覧者にも本文と接続中の利用者を表示する。4接続目は拒否し、切断後は空いた枠で接続できる。 |
| P1-2 | 認可 | 未ログイン、文書の権限なし、閲覧者からそれぞれ接続・更新を試す。閲覧者の読取りだけが許可され、拒否された更新はメモリ・配信先に現れない。認証されていてもオリジンが異なる接続を拒否する。 |
| P1-3 | 編集経路 | 相手の更新を受けた端末から、その更新を送り返さないことを通信記録で確認する。接続完了の表示に保存済みの意味を持たせない。 |
| P2-1 | 保存確認と再起動 | DBコミット前、コミット直後、`ACK` 送信直後でプロセスを止める。コミット前の更新は復元されず、コミット後の更新は同じDBから復元される。ロード完了前の本文配信はない。 `ACK` が未着の更新は端末から再送できる。 |
| P2-2 | 重複と応答 | コミット済みの `ACK` を破棄し、同一ID・同一バイト列を再送する。受理行と配信を増やさず、元の順番号で `ACK` を返す。同じIDでバイト列が異なれば拒否する。先行更新の `ACK` だけでは後続の更新が保存待ちのまま残る。 |
| P2-3 | 切断と端末復旧 | 別プロファイルの片方を切断し、双方を編集してから再接続する。配送後に本文が一致する。端末を再起動し、状態のみ・送信待ちのみが残ったデータをそれぞれ読み込む。削除だけの更新と依存のある更新を含め、残存データにある変更が `UPDATE`、DBコミット、`ACK` を経て反映される。 |
| P2-4 | スナップショット | スナップショット作成時に次の更新を保留し、スナップショットの確定後に受理する。再起動後に両者が復元される。包含済みログを整理しても過去の受理キーで再送を判定できる。 |
| P3-1 | 失効と順序 | オンライン編集中および切断中に編集権限を閲覧へ変更する。変更が確定する前に受理した更新は残り、確定後の旧版の更新はDB・配信先に現れない。閲覧は最新のサーバー本文から続けられ、拒否したローカル編集は書き出せる。再付与後に旧版の下書きを自動送信しない。 |
| P3-2 | 削除とキャッシュ | 文書を論理削除し、古い端末を接続する。旧IDは復活せず、更新も配信もない。未送信内容は書き出せる。共有ブラウザでログアウト後に別アカウントで開き、キャッシュが混ざらないことを確認する。 |
| P3-3 | 制限とエラー | 本文・更新・完全状態それぞれの上限直前、上限と超過を試す。フレームと頻度の上限も試す。破損、依存待ち、期限切れ、存在しない文書では、定めた応答を返し、拒否された更新が正式状態と配信先に現れない。依存不足は必要な差分をまとめて送ったときに復旧できる。 |
| P4-1 | デモと入力 | 手順と固定seedを使い、別プロファイルの利用者が共同編集、切断復帰、失効、サーバー再起動を再現する。日本語IME、絵文字、改行、貼り付け、個人のUndoを確認する。 |
| P4-2 | バックアップ復元 | 取得したバックアップから文書と権限を同じ時点に戻す。復元した本文の取得と、復元後の権限に沿った拒否を確認する。 |

## Phase 1の受入結果

2026年11月25日に実装コミット `49bba1344f76a3649203f4116c7dd611d65d5385` を検証した。WSL 2のx86_64でNode.js 22.22.2、npm 10.9.7、Yjs 13.6.31、Playwright 1.65.1、Chromium Headless Shell 159.0.8154.6を使った。型検査とビルドが成功し、通常の起動経路でHTMLとビルド済みJavaScriptが取得できた。

| ID | 判定 | 観測結果 |
| --- | --- | --- |
| P1-1 | 合格 | 所有者、編集者、閲覧者が別々のChromiumプロファイルで接続し、全画面に3人の名前が表示された。所有者と編集者が `abcd` の同じ位置に挿入し、互いに異なる文字を削除した。配信の保留中は `aXcd`、`abYd`、`abcd` だった。保留解除後は3画面とも `aXYd`、受理順番号5になった。4接続目はHTTP 409で拒否され、閲覧者のタブを閉じると空いた接続枠で本文と番号5を取得できた。 |
| P1-2 | 合格 | 未認証はHTTP 401、文書の権限なしと異なる `Origin` はHTTP 403。閲覧者の本文は表示され、画面から編集できなかった。閲覧者が送った `UPDATE` を `WRITE_FORBIDDEN` で拒否し、その更新の内容が他の接続にも再接続後の初期状態にも現れず、連番も増えなかった。 |
| P1-3 | 合格 | WebSocketの送信記録で `UPDATE` は所有者3件、編集者2件、閲覧者0件。5件は最初の本文と各編集者の挿入・削除に対応し、受信更新の再送は0件だった。接続完了後の表示は「接続中」で、「保存済み」「保存完了」は表示されなかった。 |

サーバー試験は4件、ブラウザ試験は同じシナリオを3回実行して3回とも成功した。ブラウザ試験では、サーバーが受理した4件の変更の配信だけを試験側で一時保留し、両者が相手の変更を適用する前に編集したことを確認した。挿入順はYjsの規則に従うため、試験では `aXYd` と `aYXd` のいずれかに全画面が一致することを判定する。

サーバー試験では破損、書式付きの更新、依存する先行更新が欠けた更新も拒否し、他端末と再接続後の本文に反映されないことを確認した。編集中のアカウントを閲覧者に変更すると既存接続を閉じ、再接続時のロールが閲覧者になった。別の試験で3接続のうち1本がWebSocketの `ping` に応答しない状態を作り、サーバーがその接続を閉じた後に空いた枠で `STATE` を取得できることを確認した。

Firefox、WebKit、実機のモバイルブラウザ、Docker Composeは未検証。SQLiteへの永続化、保存確認の `ACK`、端末内保存、オフライン変更の再送と文書削除は後続フェーズで扱う。

## 計測と検証範囲

Phase 4で100件程度の更新を使い、配送時間、再同期時間、送信量、DBの増加量を測る。件数、機器、ブラウザ、依存パッケージのバージョンを併記する。Phase 0では時間や容量の性能目標を設けない。固定seedの再現試験と上限の検査は上表の条件で判定する。停電、ディスクの喪失、複数サーバー間の復旧、未取得のアプリのオフライン起動は今回の検証範囲外とする。
